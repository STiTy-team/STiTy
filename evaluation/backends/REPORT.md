Qwen3-ASR 단일 백엔드 체제에 Voxtral Realtime과 Nemotron Streaming을 추가한다.
후보 6종 심사, 측정 방법론 확정, 백엔드 구현, 실측까지 마쳤다. 결과와 그 과정에서 확정된
함정은 8~10절에 있다.

---

## 1. 배경

STiTy의 ASR 경로는 Qwen3-ASR 하나다. "현재 스트리밍 ASR 기술 수준이 어디까지 왔는가"에
답하려면 비교군이 필요하고, 그 비교군은 **한국어를 하면서 실제로 스트리밍인** 모델이어야
한다. 이 두 조건이 후보 심사의 축이 됐다.

초기 후보는 NVIDIA Parakeet-TDT, NVIDIA Nemotron streaming, Mistral Voxtral Realtime,
Kyutai STT, Moonshine 다섯이었다. 심사 결과 둘을 채택하고 하나를 제외했으며, 목록에 없던
한 모델이 사실상 최적 후보로 올라왔다.

## 3. 핵심 발견

### F1 — 초기 후보 다섯 중 셋이 한국어를 못 한다

Parakeet v3는 유럽어 25종, Kyutai는 영어·프랑스어뿐이다. Moonshine의 한국어 변종은
존재하지만 비상용 라이선스다. STiTy가 한↔영 동시통역인 이상 이 셋은 영어 쪽 baseline
이상의 역할을 할 수 없다.

### F2 — 후보 다섯 중 둘은 애초에 스트리밍이 아니다

Parakeet-TDT와 Moonshine은 오프라인 모델이다. 청킹으로 감싸 스트리밍 비교에 넣으면
측정되는 건 모델이 아니라 **우리 커밋 정책**이다. Qwen3-ASR이 이미 그 구조이므로,
같은 교란요인을 하나 더 늘리는 셈이 된다.

### F3 — 목록에 없던 Voxtral Realtime이 최적 후보였다

Apache-2.0이고 13개 언어가 한국어·일본어·중국어·스페인어를 포함한다 — STiTy 지원
언어셋과 정확히 겹친다. 지연을 재학습 없이 80~2400ms에서 조절할 수 있고, Qwen3-ASR과
같은 vLLM 스택으로 서빙된다.

### F4 — 라이선스 통념이 반대였다: CC-BY-4.0에는 특허 그랜트가 없다

초기 검토에서 OpenMDW-1.1(Nemotron)을 "법무 확인 필요"로 표시했으나 이는 틀렸다.
OpenMDW-1.1은 **copyright + patent + database + trade secret** 에 걸쳐 무제한 권리를
부여하며, field-of-use·로열티·지역 제한이 없고 출력물에도 제약이 없다. 재배포 시 고지
유지가 유일한 의무다.

반면 Creative Commons 라이선스는 특허권을 부여하지 않는다고 본문에 명시돼 있다.
상업 배포 관점에서 확인이 필요한 쪽은 오히려 CC-BY-4.0 모델들(Parakeet, Kyutai)이다.
다만 둘 다 한국어 미지원이라 실무 영향은 없다.

## 4. 측정 방법론

### 단일 WER로는 비교가 성립하지 않는다

모델마다 지연 노브의 **단위가 다르다.**

| 모델 | 노브 | 단위 |
|---|---|---|
| Voxtral | `transcription_delay_ms` (`tekken.json`) | 밀리초 |
| Nemotron | `att_context_size = [56, R]` | 80ms 프레임 개수 |
| Qwen3-ASR | 청크 길이 + 커밋 정책 | 초 |

각자의 기본값으로 돌려 WER을 비교하면 그 차이가 *모델 성능 차이인지 지연 예산 차이인지
구분되지 않는다.*

### 실제 설정 가능한 지연 지점

| 지연 (ms) | 80 | 160 | 320 | 480 | 500 | 560 | 1120 | 1200 | 2400 | 2500 |
|---|---|---|---|---|---|---|---|---|---|---|
| Voxtral | ● | ● | ● | **◉ 기본** | | ● | ● | ● | ● | |
| Nemotron | ● | ● | ● | | | ● | **◉ 기본** | | | |
| Kyutai 1B | | | | | ● 고정 | | | | | |
| Kyutai 2.6B | | | | | | | | | | ● 고정 |
| Qwen3-ASR | *ms 노브 없음 — 초 단위 청크 + 커밋 정책이 지연을 정한다* | | | | | | | | | |

Voxtral은 80ms 배수 `[80, 1200]` 구간 + `2400`, Nemotron은 `R ∈ {0,1,3,6,13}` 에
대응하는 5점뿐이다. **겹치는 값이 거의 없다는 것이 요점이다** — 기본값끼리 비교하면
Voxtral 480ms 대 Nemotron 1120ms로, 지연 예산을 2.3배 다르게 준 채 품질을 견주게 된다.

따라서 **지연을 맞추고 품질을 재거나, 품질을 맞추고 지연을 잰다.** 어느 쪽이든 맞출
지점을 찾기 위한 최소한의 곡선이 필요하다.

> **선례**
> `arabic` 브랜치의 커밋 `4ef4c47` 은 "아랍어 static 스윕 6~9초 — 8초에서 평탄,
> **이전 결론 정정**" 이다. 한 점만 봤을 때는 "지연을 더 주면 좋아진다"였으나 곡선을
> 채우자 평탄 구간이 드러났다. 무릎점은 점 하나로는 보이지 않는다.

다만 전 데이터셋 풀 스윕은 낭비다. 채택한 절차는 **서브셋에 모델당 3점 → 지연을 맞춘
공통 동작점 확정 → 그 한 점에서만 전체 평가** 다. 스윕은 배포 방식이 아니라 동작점을
고르기 위한 일회성 측정이다.

## 5. 기술 제약

### 의존성이 공존 불가다

| 환경 | 핵심 버전 | 비고 |
|---|---|---|
| `stity` *(기존)* | torch 2.9.1+cu128 · transformers 4.57.6 · vllm 0.14.0 | Qwen3-ASR |
| `asr-nemotron` | transformers ≥ 5.13.0 | 4.57.6과 충돌 |
| `asr-voxtral` | vllm ≥ 0.20.0 · mistral-common[audio] ≥ 1.9.0 | 0.14.0과 충돌 |

세 모델을 한 env에 넣는 것은 불가능하다. 그러나 평가 하네스가 **WebSocket으로만** 서버에
붙기 때문에 이는 장애물이 아니라 전제가 된다 — 서버가 어느 env에서 돌든 무관하다.
env 분리가 정석이다.

### 레포에 오디오가 없다

평가 데이터는 git에 추적되지 않는다. 실측 결과 사용 가능한 것은 아래뿐이며,
**LibriSpeech test-other는 존재하지 않는다.** 영어 트랙은 FLEURS `en_us` 로 대체했다.

| 데이터 | 경로 | 클립 | 용도 |
|---|---|---|---|
| FLEURS ko_kr | `~/STiTy-team/datasets/fleurs/data/ko_kr` | 382 | CER · 스모크 + 스윕 |
| FLEURS en_us | `~/STiTy-team/datasets/fleurs/data/en_us` | 647 | WER · 스모크 |
| KsponSpeech | `evaluation/KsponSpeech/sample_data` | 40 | 예비 |
| ~~LibriSpeech test-other~~ | `evaluation/LibriSpeech/LibriSpeech/` | 0 | 부재 |

## 6. 통합 지점

프로덕션 서버는 3198줄이지만 ASR 엔진에 닿는 지점은 셋뿐이다.

```
Qwen3ASRStreamingServer.init_model()                  # :2756  모델 1회 로드
Qwen3ASRStreamingHandler._asr_streaming_transcribe()  # :1077  청크 → 가설 텍스트
Qwen3ASRStreamingHandler._asr_finish_streaming()      # :1308  종료 플러시
```

그리고 FSL 평가 서버가 **정확히 뒤의 두 메서드만 오버라이드**한다
(`streaming_websocket_server_fsl.py:117`, `:178`). VAD·커밋 정책·중복 가드·번역·타이밍
계측은 전부 백엔드 무관이다.

초기 검토에서 `core/modules.py` 의 `SpeechRecognizer` 추상 클래스를 채우자고 제안했으나
철회했다. 그 파일은 `origin/main` 에 존재하지 않으며 `arabic` 브랜치에만 남은 잔재다.

> **프로토콜 함정**
> `finish_done` ack는 선택이 아니다. 하네스의 `POST_FINISH_GRACE_SEC` 가 60초이므로,
> 이 ack를 보내지 않는 서버는 **파일마다 60초를 통째로 대기**하게 만든다.

### 범위에서 제외한 것과 근거

- **엔진 인터페이스 리팩터** — 동작 보존 리팩터는 회귀 게이트가 있어야 의미가 있는데,
  미검증 백엔드 둘과 함께 무인으로 돌리면 숫자가 틀어졌을 때 원인을 귀속시킬 수 없다.
- **전 데이터셋 풀 평가** — 미검증 어댑터로 몇 시간짜리 풀런을 돌리면 실패 시 그 시간이
  전부 낭비된다.
- **Voxtral 브리지** — `/v1/realtime` 이벤트 스키마를 실행해본 적이 없다. 눈 감고 브리지를
  쓰는 대신 프로브로 실제 스키마를 확보한 뒤 왕복 한 번에 정확히 짠다.

## 8. 실측 결과 (2026-09-11, 조건을 맞춘 최종 측정)

FLEURS ko_kr / en_us, ko·en 각 **50클립 동일 클립**(file_id 정렬 후 앞 50), 실시간 스트리밍,
4090 단독 점유, 입력은 세 백엔드 모두 **클립별 피크 0.5 정규화**(R7), 언어 힌트 없음(R10).
런은 `qwen3_partial`(Qwen3) · `laal2_20260911`(Voxtral) · `nemo_rc3`(Nemotron rc3) 이다.

### 정확도

| 백엔드 | 구성 | ko CER *(정규화)* | ko *(원값)* | en WER *(정규화)* | en *(원값)* | 빈 전사 |
|---|---|---|---|---|---|---|
| **Qwen3-ASR 1.7B** | 기본 | **0.0315** | 0.0320 | **0.0327** | 0.0354 | 0 |
| **Voxtral Mini 4B** | 기본 | 0.0424 | 0.0429 | 0.0526 | 0.0526 | 0 |
| Nemotron 0.6B | 기본 rc3(320ms) | 0.0785 | 0.1013 | 0.0812 | 0.0993 | 0 |

**정규화** 는 숫자 표기를 맞춘 채점이다(`itn_rescore.py`, R13). Nemotron 이 아라비아 숫자를
한 번도 출력하지 않아(50클립 중 0건, "이천십일년") 인식이 맞아도 오답이 되기 때문이다.
바뀐 클립은 Nemotron ko·en 각 10/50, Qwen3·Voxtral 은 0~1/50 이다. 순위는 양쪽 다 같다.

### 지연 — 세 축으로 나눠 잰다

| 백엔드 | 첫 표시 ko/en | 굳음 ko/en | 커밋 ko/en | 조각/클립 ko/en | rtf ko/en |
|---|---|---|---|---|---|
| **Qwen3-ASR 1.7B** | **1175 / 1054 ms** | 2125 / 1677 ms | 5607 / 6930 ms | 9.2 / 8.1 *(미확정)* · 1.2 *(커밋)* | 0.92 / 1.02 |
| **Voxtral Mini 4B** | 1302 / **917 ms** | 1302 / **917 ms** | 1302 / **917 ms** | 31.9 / 26.2 | 0.89 / 0.97 |
| Nemotron 0.6B | 1321 / 1074 ms | 1321 / 1074 ms | 1321 / 1074 ms | 12.9 / 16.2 | 0.86 / 1.00 |

| 축 | 정의 | 답하는 질문 |
|---|---|---|
| **첫 표시** | 그 단위가 화면에 처음 뜬 시각 (미확정 가설 포함) | 언제 반응이 보이나 |
| **굳음** | 그 단위가 더 이상 고쳐 쓰이지 않게 된 시각 | 언제 읽어도 되나 — **지연을 한 숫자로 말해야 하면 이 축** |
| **커밋** | 서버가 `final` 을 내보내는 시각 | 화면과 무관. **STiTy 는 번역이 커밋에서 시작하므로 통역 지연이 이 축을 탄다** |

append-only 백엔드(Voxtral 델타 · Nemotron RNN-T)는 세 축이 같은 값이다.

Qwen3 서버는 미확정 가설을 `partial` 로 계속 내보내고(최소 간격 0.12초, 클립당 8~9개)
문장이 끝나면 `final` 로 확정한다. Voxtral 델타와 Nemotron RNN-T 출력은 수정되지 않으므로
두 축이 같은 값이다. **한 축만 쓰면 어느 쪽이든 한 백엔드가 부당해진다**(R12).

읽을 수 있게 되는 시각(굳음)으로 보면 셋의 차이는 1초 미만이다. 반면 커밋축은 Qwen3 만
5.6 / 6.9초로 떨어져 있는데, 이건 계산이 아니라 정책이다 — 정책축 LAAL(서버가
`decisionAudioSec` 를 주는 Qwen3 에서만 잰다)이 4975 / 5941ms 이고 체감과의 차이
0.63 / 0.99초만이 계산 비용이다. 나머지는 "문장이 끝나야 확정한다"는 규칙이다.

확정 지연(마지막 출력 − 실제 오디오 끝)은 Qwen3 −1.05 / +0.03초, Voxtral −1.35 / −0.34초,
Nemotron −1.76 / +0.03초 — **셋 다 말이 끝나는 시점에 전사가 이미 끝나 있다.**

### 이 표를 읽을 때의 단서 둘

- **Qwen3 의 확정축은 실제보다 유리하다.** AST 파이프라인이 `VAD-FINISH → 번역 → final` 이라
  ASR 만 재려고 번역을 껐다(`--trans-backend gtx --trans-retries 1 --trans-timeout 0.05`,
  기본값은 `local` / `None` / `10.0`). 제품 경로에서는 final 이 번역을 기다리므로 확정이 더
  늦다. 첫 표시축은 번역과 무관하다.

  그 밖의 기본값 이탈은 전부 인프라 인자다 — Qwen3 `--gpu-memory-utilization 0.60`(기본 0.8),
  Voxtral `--gpu-memory-utilization 0.85` + `--max-model-len 16384`(기본 131072) +
  flashinfer 샘플러 off. **지연 노브는 셋 다 모델 기본값**이고 Voxtral 의
  `transcription_delay_ms` 는 건드리지 않았다(기본 480ms).
- **FLEURS 는 한 클립이 한 문장이고 문장 내 쉼이 없다.** 그래서 Qwen3 의 VAD 가 클립당 한 번만
  커밋한다(확정 출력 1.2개). 쉼이 있는 실제 발화에서는 더 자주 커밋되므로 **확정축은 이
  데이터셋 특성에 기댄 값**이다. 첫 표시축(청크 0.12초 간격)은 그 영향이 작다.

## 9. 규명한 함정

### R1 — Nemotron 의 정식 API 는 청크별 `generate()` 가 아니다

청크마다 `model.generate()` 를 부르면 **매 호출이 encoder/decoder 캐시를 리셋**해 청크 경계의
단어가 통째로 빠진다. 예외도 경고도 없어 전사를 눈으로 보지 않으면 못 잡는다.

```
청크별 generate  매입국 충격 신혼단계가 때문에 문화충격보다 빠르게 발생하 더 각심할 수
제너레이터 API   제입국 충격은 신혼 단계가 없기 때문에 문화충격보다 빠르게 발생하며
                 더 오래 지속하고 더 극심할 수 있습니다.
```

정답은 mel 청크를 내놓는 제너레이터를 `input_features` 로 한 번 넘기는 것이다. 노브는
`att_context_size` 가 아니라 **`num_lookahead_tokens`** 이고 0/3/6/13 만 유효하다 — 다른 값을
주면 조용히 13 으로 떨어져 **다른 이름의 같은 결과**가 저장된다.

### R2 — Voxtral 기동은 벽이 셋이었다

`0.85` + `--max-model-len 16384`(KV cache 예산), **nvcc 부재**로 인한 flashinfer JIT 실패
(`VLLM_USE_FLASHINFER_SAMPLER=0` 으로 우회, `--enforce-eager` 로는 안 풀린다),
`session.update` 의 `model` 최상위 규칙.

### R3 — Qwen3 의 "빈 전사"는 공용 GPU 경합이 아니었다

`gpu_watch.log` 가 반증했다(카드가 완전히 빈 시점이 있었고, 뒤에 올라온 PID 는 AST 서버 자기
스택). 원인은 둘이 겹쳐 있었다: **(1)** vLLM ASR(기본 0.8 = 18.6GiB) + 번역기
`madlad400-3b-mt`(7.2GiB)가 24GB 를 넘겨 mm encoder OOM → EngineCore 사망(클라이언트에는
`ConnectionClosedOK: 1000 (OK)` 로 보인다), **(2)** 파이프라인이 `[VAD-FINISH]` → 번역 →
`[AST-SEND] final` 순서라 번역이 늦으면 final 이 영영 안 나간다(서버 로그엔 전사가 있는데
`AST-SEND` 0건). 진단: `grep -c AST-SEND server.log` 가 0 이면 (2), `EngineDeadError` 면 (1).

### R4 — "주기적 commit 이 확정을 유도한다" 는 틀렸다 *(2026-09-11 정정)*

09-10 판은 "1초마다 commit 을 보내야 발화 중 출력이 나온다"고 적었다. 관찰(출력 29개 대 0개)은
사실이지만 해석이 틀렸다. vLLM 소스가 계약이다:

- `input_audio_buffer.commit` 은 **생성을 시작시키는 스위치**다. 이미 돌고 있으면
  `"Generation already in progress, ignoring commit"` 으로 무시된다(`realtime/connection.py:174`).
  주기적으로 보낸다고 확정이 더 자주 일어나지 않는다 — **첫 번째 것만 효과가 있다.**
- 끝을 알리는 건 commit 이 아니라 **`{"final": true}`** 다(`connection.py:155-157`). 이게 오디오 큐에
  종료 센티널을 넣는 유일한 수단이고, 보내면 `transcription.done` 이 온다.
  "종료 이벤트가 없어 정적 타임아웃으로 끊어야 한다"던 종전 기록도 같은 이유로 틀렸다.

즉 종전의 ci1.0 대 ci0 비교는 "확정 주기"가 아니라 **생성을 언제 시작했는가** 를 비교하고 있었다.
그 축으로 다시 재면(즉시 시작 sd0 / 2초 늦게 시작 sd2.0):

| 구성 | ko CER | en WER | LAAL_CA ko / en |
|---|---|---|---|
| 생성 즉시 시작 | 0.0429 | 0.0526 | 1302 / 917 ms |
| 생성 2초 지연 | 0.0429 | 0.0526 | 1307 / 966 ms |

**전사는 50/50 완전히 동일하고 지연 차이도 6ms / 49ms 뿐이다.** 늦게 시작해도 따라잡으므로
이 백엔드에서 commit 은 지연 노브가 아니다. 문서 흐름(commit → append → commit final)대로 쓰면 된다.

### R5 — 지연 지표가 백엔드마다 다른 것을 재고 있었다

두 가지 편향이 있었다.

1. **무음 크레딧.** `smoke_client` 는 VAD 커밋을 유도하려고 오디오 뒤에 무음 1초를 붙이는데,
   서버가 계산하는 `fsl_sec` 의 기준점이 **무음까지 포함한 오디오 끝**이었다. 무음 1초 동안의
   처리 시간이 지연에서 통째로 빠진다. Voxtral 쪽은 무음 없이 실제 끝 기준으로 쟀다.
   → 같은 축이 아니었다. Nemotron 의 이전 수치 **FSL 0.043s 는 이번 측정에서 +1.05s** 가 됐다.
2. **정의 불일치.** 한쪽은 서버가 final 마다 계산한 값의 평균, 다른 쪽은 클라이언트가 잰
   마지막 토큰 도착. `rtf` 도 클립별 연결·정적 대기(Voxtral 은 마지막 delta 후 3초)를 포함해
   오염돼 있었다.

→ 셋 다 **클라이언트에서, 무음 제외 실제 오디오 끝 기준**으로 통일했다.
다만 그 통일된 지표 자체가 여전히 클립 길이를 재고 있었다 — **R9 에서 LAAL 로 갈아엎었다.**

### R6 — 20클립 서브셋은 결론을 바꿀 만큼 흔들린다

Qwen3 ko 는 20클립에서 CER **0.0254**, 같은 정렬의 50클립에서 **0.0510** 이다(앞 20개만 다시
채점하면 정확히 0.0254 — 표본 구성 차이지 회귀가 아니다). 뒤 30클립이 0.0680 으로 더 어렵다.
**20클립 수치를 백엔드 비교에 쓰면 안 된다.**

---

### R7 — Voxtral en "빈 전사 4건"은 모델이 아니라 입력 레벨이었다

빈 클립에서도 `transcription.delta` 는 60~142건씩 온다. **전부 `delta: ""`** 다(정상 클립도
대부분 빈 델타이고, 이 4건만 끝까지 텍스트가 한 글자도 안 나온다). 서버 로그에 에러도 없다.

FLEURS en test 는 클립별 녹음 레벨이 50dB 넘게 벌어져 있고(피크 0.002 ~ 0.75), 빈 4건이
정확히 최저 레벨 구간이다:

| 구간 | 피크 | dBFS | 결과 |
|---|---|---|---|
| 빈 전사 4건 | 0.0020 ~ 0.0045 | −69 ~ −65 | 무출력 |
| 정상 최저 | 0.0051 ~ 0.011 | −64 ~ −58 | 정상 전사 |

게인만 올리면 4건 모두 정상 전사되고, **피크 0.1 / 0.5 / 0.95 에서 전사가 완전히 동일**하다
— 게인 민감도가 아니라 대략 0.005 근처의 임계값이다. Qwen3·Nemotron 은 같은 4건을 원본
레벨로도 정상 전사한다(특징 추출 단계에서 발화 단위 정규화를 하므로).

따라서 레벨은 백엔드 특성이 아니라 **입력 조건**으로 취급하고, 공용 `smoke_client.load_audio`
에 피크 정규화를 넣어 세 백엔드에 같은 오디오를 먹인다. 효과는 빈 4건에 그치지 않았다 —
저레벨 클립 전반이 좋아져 **en WER 0.1445 → 0.0526**(빈 전사를 빼고 계산했던 0.0701 보다도
낮다), **Qwen3 ko CER 0.0510 → 0.0320** 이다.

### R8 — 증분 출력은 "단어 경계"까지 고쳐야 끝난다

Nemotron 을 증분화한 첫 판에서 en WER 이 0.0959 → **0.1892** 로 두 배가 됐다. 모델이 아니라
조립이다. 클라이언트는 final 들을 `" ".join` 으로 잇는데(Qwen3 는 문장 단위 final 이라 그게
맞다), 델타가 단어 중간에서 잘리면 그 자리에 공백이 박힌다:

    lag be|hind -> "lag be hind",  ma|de -> "ma de",  depen|ding -> "depen ding"

델타를 **마지막 공백까지만** 내보내고 꼬리 단어는 다음 번으로 미뤄 해결했다(반 단어는 자막으로
띄울 수도 없으므로 소비자 입장에서도 이쪽이 맞다). 지연 비용은 단어 하나 분량이다.

두 번째 판에서는 전사가 **정확히 두 번 반복**됐다(CER 1.245). `finish()` 에서 스트리밍
누적본과 `generate()` 최종본을 대조해 "어긋나면 최종본을 따른다"고 짠 코드가 원인이다 —
둘은 같은 greedy 디코드 결과인데 공백 처리만 달라(`strip` vs `lstrip`) 매번 "어긋났다"고
판단했다. **스트리머가 한 번도 안 불린 경우에만** 최종본으로 대체하도록 좁혔다.

ko CER 은 두 버그 모두에서 0.0925 ~ 0.0933 으로 거의 안 움직였다. 조사·어미가 붙어 공백
오염의 영향이 작기 때문이다 — **같은 버그가 en 만 크게 때렸다.** 언어 하나만 보고 증분화를
검증하면 못 잡는다.

### R9 — 우리 지연 지표는 시스템이 아니라 **클립 길이** 를 재고 있었다

`ttfo_sec` · `completion_lag_sec` 은 둘 다 기준점이 "실제 오디오 끝"이다. 발화 도중에 출력하는
백엔드에서 이 값은 사실상 −(클립 길이 − 출력 시점) 이라 **클립이 길수록 좋아 보인다.**
구 8절의 "첫 출력 −9.22초"는 지연이 9.22초 짧다는 뜻이 아니라 클립이 길었다는 뜻에 가깝다.
세 백엔드의 클립 집합이 같아 순위가 크게 틀어지진 않았지만, 이 축으로는 **Qwen3 가 사실상
비증분이라는 사실이 통째로 가려진다**(−1.75초로 오히려 좋아 보였다).

레포에는 이미 표준 구현이 있다 — `evaluation/ast/metrics_ast.py` 의 `laal_for_utterance`, 그리고
AST 서버가 final 에 실어 보내는 `decisionAudioSec`(그 d_i 로 쓰라고 붙어 있다). 자체 지표를 버리고
이걸 쓴다. 세 백엔드에 공통으로 성립하는 축은 **LAAL_CA** 다(8절 정의 표).

**다만 지표를 바꾼 것만으로는 부족했다** — 어느 출력을 세느냐가 남아 있었다(R12).

조립에 함정이 하나 있다: **Voxtral 델타는 단어 중간에서 끊긴다.** 조각을 그대로 단위로 세면
26조각 → 24단위로 잡히는데 실제 문장은 19단어라 |Y_hyp| 가 부풀고, γ = T / max(|Y_hyp|,|Y_ref|) 와
τ 가 어긋나 **이 백엔드만 LAAL 이 왜곡된다.** 누적 텍스트에서 **완성된 단어** 에만 그 시점을 붙여
해결했다(Qwen3/Nemotron 의 final 은 그 자체로 완성된 세그먼트라 변환하지 않는다 — 걸면 매
세그먼트의 마지막 단어가 부당하게 다음으로 밀린다).

### R10 — 언어 힌트를 한 백엔드만 받고 있었다

Voxtral realtime 은 **언어를 지정할 방법이 아예 없다.** `session.update` 스키마는 `type`/`model`
뿐이고 프롬프트 조립(`start()` + `encode_streaming_tokens()`)에 언어 토큰이 없다 — 항상 자동
감지다. 그런데 우리는 Nemotron 에 `ko-KR`/`en-US` 를 주고 있었다. 셋 다 `auto` 로 맞췄다.

### R11 — Nemotron 의 "기본값" 은 rc13 이 아니라 rc3 이다

`config.json` 의 `default_num_lookahead_tokens` 가 **3**(320ms)이고 supported 목록도 3 이 첫 값이다.
rc13(1120ms)은 lookahead 를 최대로 준 설정이므로, 그걸 "기본값"이라 부르고 다른 둘과 비교하면
**이 백엔드에만 지연 예산을 3.5배 준 채 정확도를 견주는 것** 이다 — 4절이 경고한 바로 그 함정에
우리가 걸려 있었다.

rc3 기본값의 정확도는 ko CER 0.1013 / en WER 0.0993 으로 rc13 구판(0.0933 / 0.0886)보다 **떨어진다**
— lookahead 를 덜 주니 정확도가 낮아지는 방향 자체는 12절 스윕과 일치한다.
다만 이번 런에서 **언어 힌트 제거(R10)가 같이 적용됐으므로 차이를 lookahead 탓으로만 돌리면 안 된다.**

### R12 — Qwen3 의 미확정 채널(`partial`)을 버리고 재고 있었다

`smoke_client` 는 `type=="final"` 만 수집한다. 그런데 Qwen3 서버는 미확정 가설을 `partial` 로
계속 내보낸다(`streaming_websocket_server.py:1051`, `PARTIAL_MIN_INTERVAL_SEC = 0.12`).
AST 서버는 이를 끄지 않는다. 즉 **이 백엔드만 "확정 시각"을, 나머지 둘은 "출력 시각"을**
재고 있었다 — Voxtral 델타와 Nemotron RNN-T 출력은 애초에 수정되지 않아 둘이 같은 값이다.

프로브로 받은 실제 스트림(ko, 12.5초 클립):

```
 2.05s partial  다
 4.13s partial  다름이 수직 간격은 15m이며 공사는.
 8.17s partial  다리 및 수직 간격은 15m이며 공사는 2011년 8월에 마무리
11.53s final    다리 및 수직 간격은 15m이며 ... 2017년        <- 종전에 유일하게 센 것
```

50클립 재측정 결과 Qwen3 의 지연은 **첫 표시 1175 / 1054ms · 확정 5607 / 6930ms** 다.
종전 표의 "Qwen3 5607ms, Voxtral·Nemotron 의 5배"는 **확정축 하나만 보고 쓴 것**이고,
첫 표시 기준으로는 Qwen3 가 ko 에서 가장 빠르다.

대신 그 이른 출력은 **고쳐 쓰인다**(문자 단위로 처음 뜬 값이 최종과 다른 비율 15~67%:
"다름이"→"다리 및", "데일"→"델"). 그래서 축을 하나로 합칠 수 없고, 8절처럼 둘 다 낸다.
자막 안정성과 지연의 교환이지 성능 우열이 아니다.

### R13 — 숫자 표기(ITN)가 정확도 비교에 섞여 있다 *(정규화해서 값에 반영)*

Nemotron 은 아라비아 숫자를 **한 번도** 출력하지 않는다(ko·en 각 50클립 중 0건). FLEURS
참조는 숫자를 쓴다. 그래서 참조에 숫자가 있는 클립(ko 12 / en 10)에서만 오류율이
**0.1914 / 0.2016** 으로 뛰고, 없는 클립에서는 **0.0728 / 0.0737** 이다. Qwen3·Voxtral 은
둘 다 숫자로 출력해 그런 격차가 없다.

표의 0.1013 / 0.0993 중 **약 2%p 는 인식이 아니라 표기 규칙**이다. 서술로 끝내지 않고
`itn_rescore.py` 로 정규화해 8절 표에 실었다 — **Nemotron 0.0785 / 0.0812**, Qwen3·Voxtral 은
0.0005 이하로 움직인다.

정규화는 **참조에 실제로 있는 숫자**에 대응하는 말 표기만 숫자로 되돌린다. 가설 전체에서
한글 수사를 찾아 바꾸면 "데이"→"데2", "사육"→"46" 같은 오검출이 난다(실제로 첫 판에서 났다).
한 글자 수사는 뒤에 단위나 조사가 올 때만 되돌리고, 앞 글자가 수사면 더 긴 수의 일부로 보고
건드리지 않는다. 세 백엔드에 같은 변환을 적용하므로 어느 쪽에도 유리하지 않다.

---

## 10. 결론

1. **정확도는 기준선 Qwen3 가 두 언어 모두 1위다.** 표기 정규화 기준 ko CER 0.0315 /
   en WER 0.0327, Voxtral 0.0424 / 0.0526, Nemotron 0.0785 / 0.0812. 원값에서도 순위는
   같다(R13). **기준선을 갈아탈 이유는 나오지 않았다.**
2. **지연은 세 백엔드가 같은 급이다.** 첫 표시 0.92~1.32초, 읽을 수 있게 되는 시각(굳음)
   0.92~2.13초 — 차이가 1초 미만이다. Qwen3 가 가장 먼저 띄우고 가장 늦게 굳는다.
3. **혼자 떨어져 있는 건 커밋축이다**(Qwen3 5.6 / 6.9초). 계산이 아니라 정책이고 — rtf 0.92,
   계산 비용은 0.63초뿐 — 커밋 출력이 클립당 1.2개다. **STiTy 는 번역을 커밋에서 시작하므로
   통역 자막 지연이 통째로 이 축에 실린다.** 모델을 바꾸지 않고 줄일 수 있는 축이 여기다.
4. **단 이른 출력은 공짜가 아니다.** Qwen3 의 미확정 가설은 나중에 고쳐 쓰인다(15~67%).
   Voxtral·Nemotron 은 append-only 라 그 흔들림이 없다. 자막 안정성과 지연의 교환이므로
   UX 결정이지 성능 우열이 아니다.
5. **0.6B 가 4B 와 같은 지연을 낸다.** Nemotron 은 지연이 Voxtral 과 동급이고 rtf 는 가장
   낮다(0.86). 정확도만 뒤진다.
6. **이 작업에서 결론을 뒤집은 건 전부 모델이 아니라 측정이었다.** R4~R12 가 그 목록이고,
   마지막 R12 는 "어느 출력을 세느냐"만으로 한 백엔드의 지연을 5배로 만들었다. 백엔드
   비교에서 비싼 건 모델을 띄우는 일이 아니라 **측정이 모델을 재고 있는지 확인하는 일**이다.

## 11. 후속

- **공통 동작점 비교.** 이번 표는 전 백엔드 기본값 한 점이다. 지연 예산을 맞춘 비교는
  4절에서 설계만 해 두고 실행하지 않았다(12절 스윕이 그 준비 기록이다).
- **커밋 시점 손보기.** 커밋축이 5.6~6.9초인데 화면 텍스트는 2.1초에 굳는다. 번역을 커밋이
  아니라 굳은 시점에 걸 수 있으면 통역 자막이 3초 이상 빨라진다.
- **커밋 정책 전제 불일치.** 중복 가드는 Qwen3 가 이전 텍스트를 수정한다는 전제 위에 있는데,
  Nemotron 은 RNN-T 라 절대 수정하지 않는다.
- **ITN 후처리.** Nemotron 을 실제로 붙이면 숫자 표기 변환이 필요하다(R13).
- 전 데이터셋 풀 평가는 범위 밖이다 — 50클립 서브셋으로 판단하고 표본 민감도는 R6 에 남긴다.

## 12. 참고 — 지연 스윕 (2026-09-09, 기본값 비교와는 별개)

동작점을 고르려고 Nemotron 만 lookahead 를 스윕한 기록이다. **이 수치들은 무음 크레딧이 있는
옛 지표(서버 측 FSL)로 잰 것**이라 8절 표와 같은 축이 아니다. 형태만 참고할 것.

| lookahead | 지연 | ko CER | 옛 FSL | RTF |
|---|---|---|---|---|
| rc0 | 80ms | 0.1191 | 0.577 | 1.253 |
| rc3 | 320ms | 0.1049 | 0.037 | 1.111 |
| **rc6** | **560ms** | **0.0932** | 0.037 | 1.100 |
| rc13 | 1120ms | 0.0960 | 0.043 | 1.103 |

**rc0(80ms)은 완전히 지배당한다** — 정확도·지연·RTF 셋 다 최악이다. lookahead 를 줄이면 청크가
잘게 쪼개져(`8*(right+1)` 프레임) 호출 오버헤드가 절감분을 통째로 먹는다. 기본값 한 점만 봤으면
"짧게 잡으면 빨라진다"로 잘못 적었을 것이다. rc6 과 rc13 의 CER 차이는 0.003 수준이다. **이 표가 "기본값" 이라 부른 rc13 은
기본값이 아니다**(R11) — 모델 기본값은 rc3 이고, 8절은 그쪽 설정이다.
