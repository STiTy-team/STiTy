## 재추출 진단 — judge25 의 채택이 무엇이었는지 (2026-09-19)

judge25 가 dev 관문을 통과한 첫 런이라 무엇이 뒤집혔는지 직접 쟀다. **같은 dev 500 문장·같은 두
프롬프트를 분절만 새로 뽑아** 다시 잰 것이다($4.45, 327초, `tools/autoseg_en2x/judge25/redraw.sh`).

| | v0 | 채택본 | Δ | 95% CI | 관문 |
|---|---|---|---|---|---|
| 추출 1 (판정에 쓴 것) | 0.5514 | 0.5652 | +0.0138 | [+0.0032, +0.0240] | 통과 |
| 추출 2 (새로 뽑음) | 0.5578 | 0.5615 | **+0.0037** | [−0.0082, +0.0152] | **탈락** |
| test 560 (독립 문장) | 0.5560 | 0.5490 | −0.0070 | [−0.0180, +0.0036] | — |

**문장이 같으므로 "dev 분포에 피팅됐다" 는 배제된다.** 바뀐 것은 모델이 분절을 다시 뽑았다는 것뿐인데
Δ 가 3분의 1 이 되고 하한이 0 아래로 내려간다. 추출 2 였다면 judge25 는 아무것도 채택하지 않았다.

사라진 0.0101 의 내역: **v0 가 0.5514 → 0.5578 로 +0.0064**(기준선이 낮게 뽑힌 몫), 채택본이
0.5652 → 0.5615 로 −0.0037. **기준선 한 벌은 후보 전부가 공유하므로 그게 낮으면 후보가 다 같이
올라간다** — judge25 이터 2 에서 서로 다른 편집 넷 중 셋이 동시에 하한 > 0 이었던 게 그 자국이다.

부트스트랩이 틀린 게 아니다. 두 추출 Δ 의 차 0.0101 은 각 Δ 의 sd 0.0058 로 보면 1.35σ 라 서로
모순이 없다. **쫓는 효과(≈+0.005)가 반폭(±0.011)과 같은 크기인데 후보를 16번 들여다보고 최고의
하한만 보는 것**이 관문이 새는 지점이다.

이 진단에서 또 하나 드러난 것: `loop_judge` 에는 "하한이 애매하면 새 분절로 다시 잰다" 는 확인
경로(`verdict == "confirm"`)가 내내 있었는데, **judge20~25 여섯 런이 전부 `--adopt-strong 0` 이라
`lo > strong` 이 곧바로 accept 로 빠져 한 번도 안 탔다.** judge26 부터 `--adopt-strong 0.05` 로
모든 채택이 확인을 거치게 했고, 확인이 후보만이 아니라 **기준선도 다시 뽑도록** 고쳤다.

## 읽을 때 주의

- **judge20 은 테스트 문장 수가 296 이라** 다른 런과 절대값을 비교할 수 없다. Δ 는 비교 가능하다.
- **judge21 의 `curve.json` 은 합본 실험 값으로 덮였다.** 근소 기각 편집을 재느라
  `--run-id judge21` 로 `--score-only` 를 돌렸고, 그때 산출물이 채택본 값을 밀어냈다. 위 표의
  judge21 수치는 **런 로그**(`logs/judge21.log`, 01:29:07 줄)에서 가져온 것이다. 산출물이 덮여도
  로그는 남는다 — 로그를 지우지 않는 규칙이 이 자리에서 값을 했다.
- **judge08 은 오라클이 0.5595 로 다르다.** 라벨 정의가 다른 시기의 런이라 나머지와
  같은 축이 아니다. 채택된 개정이 없어 채택본이 곧 v0 다.
- **분절 캐시는 런이 아니라 `--from-run` 쪽에 있다.** 루프가 `<런>/cache` 를 `../<from-run>/cache`
  로 심볼릭 링크하므로 같은 from-run 을 쓰는 런들은 **같은 분절 결과를 공유한다**(run28: judge20·21·22 /
  run29: judge23 / run30: judge24·25). 좋은 면은 judge24 와 judge25 의 v0 가 문자 그대로 같은
  한 벌이라 두 런의 Δ 비교가 깨끗하다는 것이고, 나쁜 면은 **judge21 → judge23 → judge24 의
  "단조 상승" 이 서로 다른 세 기준선 추출 위에서 잰 값**이라는 것이다. 그 상승분 0.0106 이 방법
  개선인지 기준선이 바뀐 것인지 세 점으로는 못 가린다.
- 최종 test 를 돌리지 않은 런(judge03~judge07, judge09~judge12, judge14, judge17, judge18)은
  여기 없다. 그 런들의 dev 단계 채택 이력은 각 런의 `history.json` 에 있다.
