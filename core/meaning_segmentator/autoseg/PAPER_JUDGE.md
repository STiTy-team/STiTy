# autoseg-judge — 논문 기재용 정리

판단형 프롬프트 루프(`loop_judge`)를 논문 항목별로 옮겨 적은 문서다. 설계 근거의 원본은
[LOOP_JUDGE.md](LOOP_JUDGE.md)(루프 자체), [AUTOSEG_DETAILS.md](AUTOSEG_DETAILS.md)(지표
선택과 기각 목록), [README.md](README.md)(실행과 산출물)이고, 여기서는 그 셋에서 논문에
들어갈 것만 골라 **방법 → 측정 → 결과 → 한계** 순으로 다시 세운다. 수치는 전부 실측이며
어느 런에서 나왔는지 함께 적었다.

2026-09-15 기준. `judge08` 은 끝났고 `judge09` 는 iter 4 까지 재고 멈췄다. `judge10` 이
3분할(§4)로 돌고 있다. 조각 번역 캐시 키를 고치기 전에 잰 dev-B·test 값은 쓰지 않는다(§9.11).

## 1. 문제 설정

스트리밍 번역에서 문장을 언제 끊어 내보낼지 정하는 문제다. 시스템은 소스 문장을 조각으로
나누고, 각 조각을 **따로** 번역해 순서대로 내보낸다. 듣는 사람은 되돌아갈 수 없다(무수정
제약). 따라서 경계 하나를 잘못 잡으면 그 시점에 이미 틀린 문장이 나가고, 뒤 조각이 고쳐도
사용자가 본 것은 되돌릴 수 없다.

**분절 정책을 점수 함수로 둔다.** 정책은 소스 문장만 보고 모든 후보 경계에 0~100 점수를
매긴다. 지연 예산이 정해지면 결정론적 절단기가 점수 상위 k개만 남긴다.

```
입력   Every <SEG:?> candidate <SEG:?> position <SEG:?> is <SEG:?> pre-marked
출력   Every <SEG:31> candidate <SEG:88> position <SEG:12> is <SEG:64> pre-marked
절단   k=1 → "Every candidate ‖ position is pre-marked"
```

이 형태에서 나오는 성질 셋이 실험 설계를 결정한다.

1. **지연은 프롬프트가 못 건드린다.** k(또는 예산 T)가 밖에서 정해지므로 정책은 지연을
   바꿀 수 없고, 목적함수가 "이 지연에서 품질 최대화" 하나로 줄어든다. 품질과 지연을
   가중합하는 절차는 문헌에 없다(SimulST/StreamST 7편 전부 노브를 스윕해 곡선을 그린다).
2. **문장 안의 순서만 읽힌다.** 절대 눈금은 의미가 없다. 그래서 채점 잡음을 줄일 때도
   점수가 아니라 **순위**를 평균한다(§6.2).
3. **한 번의 채점이 모든 지연을 커버한다.** 점수 벡터는 문장당 한 번만 뽑고 k 를 1부터
   훑으면 순위 전체가 채점된다. LLM 비용은 k 에 비례하지 않는다.

정책은 프롬프트 하나다. 이 연구가 자동화하는 것은 **그 프롬프트를 쓰는 일**이다.

## 2. 목적함수 — `H_set`

절단집합 하나를 통째로 재는 자다. 구현은 [`runtime/hset.py`](runtime/hset.py).

```
H_set(S) = CometKiwi(src = 원문 전체,  mt = MT(조각1) ⊕ … ⊕ MT(조각k+1))
           × (1 − max contra(S))

contra_j = NLI(premise = 원문 전체, hypothesis = 경계 j 까지의 원문 조각) 의 모순 확률
```

- 앞항(**cohesion**)은 조각으로 나눠 번역한 결과가 원문 전체를 얼마나 담는지 잰다.
  **사람 참조 번역이 필요 없다.**
- 뒷항(**contradiction**)은 그 집합에서 가장 위험한 절단 하나로 벌한다. 평균이 아니라
  최댓값인 이유는 사용자가 본 오류 한 번이 되돌려지지 않기 때문이다.
- 번역기는 `google/madlad400-3b-mt`(로컬), QE 는 CometKiwi, NLI 는
  `vicgalle/xlm-roberta-large-xnli-anli`.

### 2.1 왜 참조를 안 쓰나

참조를 자기 시스템의 offline 번역으로 두면 **어순을 단조화한 좋은 분절이 감점된다.**
통제된 최소쌍 실측:

| 변이 | COMET |
|---|---|
| `benign_minimal` (동의어·음역 차이) | 0.9308 |
| `benign_paraphrase` (구조까지 바꾼 재서술, 의미 보존) | **0.8414** |
| `negation_flip` (부정 뒤집힘 — 실제 오류) | 0.8843 |

의미를 보존한 재서술이 부정 뒤집힘보다 낮다. 편향의 크기가 실제 오류와 혼동될 수준이다.
문헌의 해법(단조 참조, 타깃 재배열)은 우리가 "그 절차 없이 된다"고 주장하는 대상이라
도입하면 컨트리뷰션이 상쇄된다. 그래서 주지표에서 참조를 뺐다.

### 2.2 왜 곱인가 — 합본만 보면 복구가 실패를 가린다

```
좋은 분절  ⟹  합본 ≈ 전체 번역     (성립)
좋은 분절  ⟸  합본 ≈ 전체 번역     (성립 안 함)
```

나쁜 경계로 잘려도 뒤 조각이 결손을 메우면 합본은 통과한다. 그러나 사용자는 t1 시점에
이미 틀린 것을 봤다.

```
원문        그건 문제가 안 될 것 같은데
나쁜 분절   그건 문제가 ‖ 안 될 것 같은데
t1 출력     "That's a problem"              ← 의미 정반대. 무수정 제약상 되돌릴 수 없다
t2 출력     "...probably won't be an issue"
합본        통과
```

그래서 방출 시점을 따로 재는 항(contradiction)이 곱으로 붙는다. 곱이라 새 상수가 안 생긴다.

### 2.3 gold 로 한 검증

test 100문장 · 3타깃 · 사람 참조 COMET-DA(T 격자 4/6/8/12 평균), `min_gap=3` 시절 값:

| 라벨 정의 | gold 격자평균 | 고른 절단의 소스 contra 평균 | contra>0.5 절단 (T=6, 252개 중) |
|---|---|---|---|
| 무절단 (상한) | 0.8770 | — | — |
| **cohesion × (1 − contra)** | **0.7780** | 0.011 | **0** |
| cohesion 단독 | 0.7823 | 0.038 | 3 |
| 참조 COMET (ref = MT(원문 전체)) 단독 | 0.7809 | — | — |
| `(1 − contra) × adequacy` (종전 정의) | 0.7685 | 0.013 | 0 |

읽는 법: **gold 최댓값을 택하지 않았다.** `cohesion` 단독이 T=6·8 에서 0.006~0.008 높지만
(유의), 그 차이는 gold 가 구조적으로 못 보는 것(조기 방출)을 사는 값이다 — gold 는 합본만
채점하므로 §2.2 의 실패를 정의상 볼 수 없고, 실제로 `cohesion` 단독이 고른 절단의 소스
contra 평균은 곱을 붙였을 때의 3.5배다.

무참조판과 참조판(ref = 로컬 번역기의 전체 번역)은 품질이 같았고(0.7823 vs 0.7809, T별
차이 전부 비유의) 지연은 무참조판이 0.2~0.4어절 빨랐다. 모델을 하나 덜 올리므로 무참조판을
쓴다.

## 3. 경계별 라벨과 기준선

`H_set` 은 집합을 재고, 오라클과 사례는 **경계 하나**를 재는 값이 필요하다. 구현은
[`runtime/labels.py`](runtime/labels.py).

```
label_j = (1 − contra_j) × (adq_left_j + adq_right_j) / 2      (타깃 평균)
```

`contra` 는 **소스 NLI** 다 — premise 가 원문 전체, hypothesis 가 `units[:j]`. 번역 NLI 로
재면 타깃 간 순위상관이 0.21 로 라벨 성분 중 가장 타깃 종속적이었는데, 원문끼리 재면
번역기가 안 끼어 타깃이 무엇이든 같은 값이고 세 타깃 평균과 +0.42 로 어느 단일 타깃보다
잘 맞는다(dev, 2026-09-13). gold 손해도 없었다(격자평균 0.7642 → 0.7685).

소스 NLI 와 번역 NLI 는 서로 다른 실패를 본다. dev 4,259 경계 중

- 소스만 모순인 자리 84곳 — `his wife was ‖ not hurt`. 부정어가 뒤에 오는 교과서적 조기
  방출인데 번역 contra 는 0.01 이다.
- 번역만 모순인 자리 174곳 — `Edinburgh Sheriff ‖ Court`. 원문은 미완일 뿐인데 번역기가
  뜻을 확정한다.

라벨은 소스 쪽만 쓴다.

### 3.1 네 기준선

전부 같은 자(`H_set`)로 잰다. 괄호는 test 100문장 gold COMET-DA(3타깃, `min_gap=3` 시절).

| 기준선 | 무엇 | test gold |
|---|---|---|
| 무분절 | 문장 통째 번역 | 0.8770 — T=∞ 참고선, 상한 |
| 집합 탐색 최적 | T마다 절단집합을 조합 탐색. 오프라인 교사만 도달 | 0.7919 |
| 중첩 제약 하 최적 | 점수 벡터 **하나**로 모든 T 를 동시에 커버할 때의 천장 | **미측정** ← 루프의 진짜 목표선 |
| 그리디 오라클 | 경계별 라벨 상위 k개 | 0.7780 |
| 정책 (`minimal_tgt`) | 프롬프트가 낸 점수 | 0.7686 |

**탐색 최적이 그리디 오라클을 gold 에서도 이겼다**(네 T 전부 유의). 경계별 값의 상위 k개를
고르는 것과 집합으로 최적인 것의 차이가 T=4 에서 +0.0284, T=6 에서 +0.0216 이다. 경계별
라벨이 절단 **하나**를 가정하고 재는 값인 반면 실제 조각의 양옆은 이웃 절단이 정하기
때문이다.

중첩 제약 하 최적을 아직 못 쟀다는 것이 이 연구의 큰 미해결이다. T별 최적 집합이 서로
중첩인 문장이 test 100 중 42% 뿐이라 **0.7919 는 점수 벡터 하나로는 도달할 수 없는 값**이고,
따라서 "정책이 탐색 최적에 얼마나 못 미치는가"를 곧바로 루프의 실패로 읽으면 안 된다.

## 4. 데이터

| | 값 |
|---|---|
| 코퍼스 | FLEURS, 소스 영어 (`fleurs-en-multi-x`) |
| 타깃 | Chinese / Japanese / German / Spanish (4타깃 평균) |
| 분할 | `run16` 의 층화 분할을 그대로 물려받음. seed `20260806` |
| v0 작성용 | 어느 분할에도 안 들어간 문장에서 프로파일 20 / 예시 8 |
| `min_gap` | 1 (판단형 런에서 코퍼스 유도값 3 을 덮어씀) |
| k | 1~10. 평균 조각이 2어절 미만이 되는 k 는 안 잰다 |

**분할을 쓰는 방식이 두 가지다.** 소스 런에 `data/test_a.json` 이 있으면 3분할로 돈다.

| 쓰임 | 2분할 (`run25`) | 3분할 (`run26`) |
|---|---|---|
| 사례·실측 예시 출처 | dev-A 150 | **train 200** (1,607 짝) |
| 채택 판정 (선별 + 본채점) | dev-A 150 (1,236 짝) | **test-A 200** (1,651 짝) |
| 체크포인트·유망 확인·최종 표 | dev-B 265 = dev 나머지 65 + train 200 | **test-B 200** = dev 나머지 65 + 옛 test 100 + 추가 35 |
| 최종 홀드아웃 | test 100 | 없다 — test-B 가 겸한다 |

**3분할로 가른 이유는 예시 유출이다.** 2분할에서는 사례를 dev-A 에서 뽑고 그 문장의 실측
라벨을 프롬프트 `[Examples]` 에 넣은 뒤 같은 dev-A 에서 채점했다 — 그 문장만 정답을 보고 푸는
셈이다. judge09 iter 2 의 dev-A Δ +0.0105 중 +0.006 이 예시로 넣은 3문장 몫이었고, 그 셋을
빼면 +0.0044 [−0.0079, +0.0161] 이다. 3분할에서는 출처(train)와 판정(test-A)이 겹치지 않는다.
분할과 별개의 방어로 `example_sentences` 가 프롬프트 `[Examples]` 에 들어간 문장을 어느
판정에서든 뺀다.

**v0 의 프로파일·예시 문장을 분할 밖에서 뽑는다.** dev 에서 뽑으면 그 문장이 프롬프트 안에
그대로 들어간 채 dev 에서 채점된다. 라벨 유출은 아니지만 그 문장에서만 유리해진다.

**v0 후보도 판정 집합이 아니라 사례 집합에서 고른다.** 판정 집합에서 고른 v0 는 그 집합에서
낙관 편향이라, 뒤따르는 개정이 부풀려진 기준선을 넘어야 한다.

**런끼리 프롬프트를 물려받지 않는다.** 앞선 런의 채택본이나 출처표를 다음 런이 이어받으면
런을 거듭하며 판정 집합에 맞춰 가고, 런끼리 비교도 할 수 없다. 매 런은 자기 v0 를 생성해
시작한다.

## 5. 파이프라인

한 이터레이션의 흐름이다. LLM 이 판단하는 곳은 넷(Writer/Critic/PE/부검)뿐이고, 형식 검증·
절단·채점·선별·채택 판정·롤백은 전부 결정론적 코드다.

```
v0 생성 (Writer, 런당 1회, 후보 2개 중 사례 집합 H_set 로 선택)
  ↓
① 현재 프롬프트로 판정 집합 채점 (k_samples=3)  → 점수 벡터
② k=1..10 절단 → 조각 번역(캐시) → H_set
③ 사례 선정 — 사례 집합에서 오라클 대비 손해가 큰 (문장, k) 12개, 지연 구간별로 고르게
④ Critic — 사례와 직전 개정의 부검을 읽고 판단 기준 수정안 또는 예시 쌍 (최대 3건)
⑤ PE — 개정 후보 N개. 번호 붙은 단위를 편집하고, 후보마다 보폭 제약이 다르다
⑥ 선별 — 판정 집합에서 돌려 뽑은 50문장으로 후보를 재고 하나만 남긴다
⑦ 본채점 → 쌍체 부트스트랩 → 채택 / 경계선 재확인 / 유망하면 dev-B 합산 / 기각
⑧ 개정 부검 — 어디가 어떻게 움직였는지 + 그 설명 한 문단
⑨ 2 이터마다 체크포인트, 나빠졌으면 롤백
  ↓
최종 test — 채택본과 v0 를 같은 자로, 그리디 오라클과 함께
```

### 5.1 프롬프트 구조

섹션 다섯이 정해진 순서로 들어간다. 골격 검사가 결정론으로 확인한다.

| 섹션 | 내용 | 편집 |
|---|---|---|
| `[Role]` | 무엇을 하는 모델인가 | 동결 |
| `[Core Principles]` | **판단 기준** — 각 자리에서 의미에 대해 던질 질문 | PE 가 고친다 (단위 `C1`…) |
| `[Scoring Rules]` | 측정 절차를 서술하는 **유일한 자리** — cohesion·contra 가 무엇이고 어떻게 곱하는지, 결합식과 순위 규칙 | 동결 |
| `[Output Rules]` | 출력 형식만. 점수의 뜻은 `[Scoring Rules]` 를 가리킨다 | 동결 (Writer 가 코드가 준 블록을 그대로 복사) |
| `[Examples]` | 소스 언어 예시 Input/Output 쌍 3~4개, 최대 8개 | PE 가 고친다 (단위 `E1`…) |

측정 절차를 두 곳에 쓰면 라벨을 바꿀 때 한쪽만 고쳐져 한 프롬프트 안에 서로 다른 목표
설명이 남는다. 그래서 `[Scoring Rules]` 한 곳으로 몰았다.

**점수를 내는 절차를 따로 적는 절은 두지 않는다.** PE 는 `[Core Principles]` 만 고치므로,
절차를 적은 절이 따로 있으면 그 안의 옛 힌트가 개정과 어긋난 채 남는다. judge09 v0 에서
그랬다 — 그 절은 원칙의 두 판단(contra·cohesion)을 순서로 다시 쓴 것에 영어 절 구조 힌트를
보탠 것이었다. 순위 규칙(마커마다 다른 정수, 넓은 범위)은 코드가 만드는 `[Output Rules]` 에
있다. 골격 검사가 허용 목록에 없는 섹션을 반려한다.

**Writer 지시문의 핵심 요구는 "표면형 규칙을 쓰지 말 것"이다.** 기능어 목록도, 구두점
규칙도, "앞 토큰이 X이면" 도 금지다. 문법 라벨도 기준이 아니라고 명시한다 — 완결된 두 절
사이의 절단이 나쁘게 측정되기도 하고 구 안쪽 절단이 좋게 측정되기도 한다.

### 5.2 분절기와 형식 검증

- 입력은 **후보 자리가 이미 전부 `<SEG:?>` 로 찍힌 문장**이다. 후보는 양끝에서 `min_gap`
  미만인 자리를 뺀 전부다. 모델은 `?` 를 정수로 바꾸기만 한다.
- 검증(`validate_scored`)이 잡는 것 셋: 마커를 뺀 본문이 원문과 다름(`text_modified`),
  입력에 있던 마커가 빠짐(`markers_missing`), 점수를 안 채운 마커가 남음(`unscored_marker`).
- 입력에 없던 자리에 모델이 새로 찍은 마커는 정규화 단계가 조용히 버린다. run15 test 의
  포맷 실패 12건이 전부 이 형태였다.
- 한 호출에 문장 6개를 묶는다(`--batch-size 6`). 12 부터는 1차 통과율이 0.75/0.27 로 무너져
  비용이 U자로 되돌아온다.
- 위반은 이터마다 `violations.json` 에 규칙별 건수와 문장 id 로 남긴다. 통과율 숫자만
  남기면 떨어졌을 때 무엇이 깨졌는지 재현 실험으로만 찾게 된다.

### 5.3 사례 — 스칼라가 아니라 반사실 쌍

Critic 에게 넘기는 단위는 "문장 #37 이 0.08 손해" 같은 숫자가 아니라 **두 절단집합의
대조**다.

```
문장 #37, k=6      정책 H_set 0.71 / 목표 0.79  (−0.08)   평균 조각 3.2어절 (구간 ≤5)
정책 절단   … the company, ‖ which had lost money for years, ‖ finally turned a profit
목표 절단   … the company, which had lost money for years, ‖ finally turned ‖ a profit
정책만 고른 자리 A("company," 뒤)   경계별 H 0.79 (문장 내 상위 20%)  coh 0.81  contra 0.02
목표만 고른 자리 B("turned" 뒤)     경계별 H 0.52 (하위 40%)
양쪽 절단의 조각 번역 (zh/ja/de/es)
```

**사례는 지연 구간마다 고르게, 문장당 하나씩 뽑는다.** 손해 상위만 뽑으면 한 구간에 몰린다.
judge05 는 12개가 전부 평균 조각 2~3.5어절이었고 모순 절단 하나로 집합이 0 이 된 경우뿐이었다.
Critic 은 그걸 "뒤집힐 수 있는 자리를 더 피하라"로 일반화했고, 넣을 때마다 짧은 조각 구간이
떨어져 iter 2~5 가 전부 기각됐다(Δ −0.014 ~ −0.038). 지연 구간은 평균 조각 길이로 ≤3 / ≤5 /
≤7 / ≤10 / ≤99 어절 다섯이다.

사례에 붙는 표식 둘:

- `latency_bin` — 위 구간. Critic 지시문은 "짧은 구간에서는 좋은 절단집합이 원래 촘촘하다"고
  알려, 절단 자체를 일반적으로 피하라는 규칙이 나오지 않게 한다.
- `contra_kill` — 정책 절단 하나의 contra 가 0.5 이상이라 집합이 0 이 됐고 목표 쪽은 아닌
  경우. 이건 "이 한 자리가 나중에 뒤집힌다"는 말이지 "짧은 조각이 나쁘다"가 아니라고
  지시문에 못 박았다.

### 5.4 Critic

입력은 사례 묶음 + 현재 프롬프트 + 직전 개정의 부검(`last_revision`)이다. 부검에는 그 개정의
판정, Δ, 지연 구간별 평균 Δ, 나빠진·좋아진 짝 수, `why`/`blamed`/`lesson` 이 들어간다 —
기각된 개정을 말만 바꿔 다시 내지 않게 하는 재료다. 출력은 JSON 이고 **토큰 조건을 받지
않는다.**

```json
{"findings": [
  {"diagnosis": "무엇을 오판했나 — 한 문장",
   "evidence": "몇 사례가 이걸 보이고 무엇이 공통인가",
   "edit": {"where": "core_principles" | "examples",
            "action": "add" | "replace",
            "target": "고칠 줄의 첫 몇 단어",
            "text": "새 문장 또는 예시 쌍"}}]}
```

제약: 최대 3건, 사례를 많이 설명하는 순. 원문 인용은 40자 이내, 특정 문장을 지목 금지,
토큰 목록 금지. 코드(`clean_findings`)가 이 계약을 어긴 finding 을 걸러낸다.

**왜 토큰 조건을 버렸나.** 이전 루프(`loop_distill`)의 Critic 은 실패를 `left_last` /
`right_first` 같은 토큰 조건으로 내고 관문이 그 매칭으로 규칙을 검증했다. 규칙 하나가 dev
3,399 경계 중 **3~5자리**에만 걸리는데 개정 한 번이 남긴 경계의 37%를 흔들어, 규칙의 직접
효과가 교란에 완전히 묻혔다. 손으로 쓴 판단 기준 프롬프트가 그 루프가 6런 동안 못 넘은
v0 를 한 번에 넘긴 것이 결정적 증거다(dev overlap 0.4767 → 0.5485).

### 5.5 Prompt Engineer — 다시 쓰지 않고 편집만 한다

**모델은 글자 수를 못 센다.** judge01 에서 Writer 는 "8,000자 이하" 지시에 10,947자를,
PE 는 상한 9,000 에 9,895자를 냈다. 초과량을 알려 되돌려도 안 줄었다(judge03: 다섯 번 중
네 번 실패, 그중 두 번은 더 길어짐). 1만 자를 통째로 다시 쓰는 한 길이는 모델 손을 떠난다.

그래서 PE 의 출력 단위를 **편집 목록**으로 바꿨다.

- 입력의 `units` 에 `[Core Principles]` 한 줄(`C1`…)과 `[Examples]` 한 쌍(`E1`…)마다 본문과
  실제 글자 수를 준다.
- 출력은 `replace` / `delete` / `insert_after` 목록. `C0`·`E0` 뒤에 끼우면 섹션 맨 앞,
  `C_end`·`E_end` 는 맨 뒤다.
- 적용과 길이 계산은 코드(`apply_edits`)가 한다. 동결 섹션은 구조상 건드릴 수 없다.

**길이 상한**은 직전 채택본 × (1 + `growth_per_iter`, 기본 0.10) 와 시작 길이 ×
`growth_ceiling`(기본 1.3) 중 작은 쪽이다. 시작 길이에 고정하면 한 번 채택된 뒤 여유가
사라지고(judge04: 상한 8,664 에 채택본 8,652자 → iter 2~4 전부 길이로 반려), 증가율만 두면
이터마다 쌓인다(10% × 5이터 = 1.61배).

**여유는 글자와 단어로 함께 준다.** LLM 은 글자 수를 못 세지만 단어 수는 어림한다.
judge05~08 에서 5% 여유(약 500자)는 원칙 하나 크기였는데 PE 가 그걸 몰라 추가만 하고 줄이지
않은 편집이 초과 6건 중 5건이었다. 그래서 `size.headroom` 에 남은 글자·단어, 원칙 한 줄의
평균 단어 수, 그 여유가 원칙 몇 개 분량인지를 함께 싣는다.

**상한을 넘기려면 근거로 자리를 만든다.** 단위마다 출처가 붙는다.

| 필드 | 뜻 |
|---|---|
| `origin` | `v0`, 또는 이 텍스트를 넣은 채택 이터 |
| `adopted_delta` / `adopted_ci_lo` | 그 채택에서 잰 Δ 와 CI 하한 (v0 단위는 null — 하나씩 잰 적이 없다) |

PE 지시문은 근거 약한 단위(v0 이면서 이번 소견이 지적한 것)부터 갈아끼우고, 이득이 측정된
단위는 뜻을 지킨 채 압축만 하라고 말한다. 압축은 `"kind": "paraphrase"` 로 표시돼
`pe_edits.json` 에 남는다. 압축도 분절기에게는 개정이므로 새 규칙과 같은 후보로 함께 재진다 —
효과를 따로 가를 수는 없고, 나빠지면 후보째 기각된다. 출처표는 한 런 안에서만 쌓인다.

**부분 실패를 통째로 버리지 않는다.** 없는 id, 섹션 헤더가 든 본문, 쌍이 아닌 예시, 같은
단위를 두 번 고치는 편집은 **그것만 빼고** 나머지를 적용한다(`pe_edits.json` 의 `skipped`).
judge07 iter 1 은 편집 넷 중 하나가 없는 id `C7` 을 가리켜 이터 하나를 통째로 날렸다.
남는 편집이 없거나, 적용 결과가 길이·골격·동결 검사에 걸리거나, 예시가 8개를 넘으면 반려한다.

길이만 넘은 경우는 편집별 실측 증감(`size_feedback.your_edits`)과 초과량(글자와 단어 둘 다)을
붙여 **한 번** 되돌린다. 콜 하나가 이터레이션 하나를 날리는 것보다 싸다.

### 5.6 개정 후보 여러 개와 선별

`--pe-candidates N` 이 2 이상이면 이터마다 PE 를 N 번 불러 서로 다른 개정을 받는다. 두
번째부터는 앞선 후보의 편집 요약을 `sibling_candidates` 로 넘겨 같은 방향을 피하게 한다.

- 후보는 판정 집합에서 **이터마다 시드로 돌려 뽑은** `--screen-n` 문장(기본 50)에서 먼저
  재고, 현재 프롬프트와의 짝 부트스트랩 Δ 평균이 가장 높은 하나만 판정 집합 전체로
  본채점한다. 선별에 쓴 문장은 분절 캐시에 남아 본채점에서 다시 돈이 들지 않는다.
- **선별 문장을 늘 같은 앞 50으로 두면 안 된다.** 거기에 맞는 후보가 이터마다 살아남고, 그
  50이 든 본판정 Δ 도 그만큼 부풀려진다. 그 이터가 쓴 인덱스는 `screen.json` 에 남는다.
- 선별에서 진 후보는 `screened_out` 으로 이력에 남아 PE 가 같은 방향을 또 내지 않게 한다.
- 후보들의 분절(API 대기)은 스레드로 동시에, 번역·QE(GPU)는 차례로 한다. 선별 한 후보에
  23분이 걸렸는데(judge08 iter 3) 대부분이 API 왕복 대기라 겹치면 셋이 그 시간에 끝난다.
  분절 캐시는 경로당 인스턴스 하나만 둔다(`JsonCache.shared`) — 스레드마다 만들면 서로의
  항목을 모른 채 같은 파일을 덮어쓴다.
- `--screen-skip` 이면 선별 최고 후보의 Δ 평균이 0 이하일 때 본채점 없이 기각한다. 부검은
  선별 문장으로 하고 `regression.json` 에 `screened_only` 로 표시한다. 본채점($2, 30분)을
  아껴 같은 예산으로 시도 횟수를 늘리는 쪽이다.

**후보마다 보폭을 다르게 준다**(`--candidate-roles`). 후보 j 는 `roles[j % len]` 의 제약을
받고, 코드(`enforce_role`)가 어긴 편집을 뺀다.

| 역할 | 제약 |
|---|---|
| `free` | 제약 없음 |
| `examples_only` | `[Examples]` 단위만 고친다 |
| `single_small` | 편집 하나, 새 본문 60단어 이내 — 효과를 그 편집에 돌릴 수 있다 |
| `rewrite` | PE 가 아니라 Writer 가 `[Core Principles]`·`[Examples]` 를 새로 쓴다 |

`rewrite` 는 v0 때 재료(프로파일·실측 사실·표본 문장·`[Output Rules]`)에 현재 프롬프트와
Critic 소견·부검 교훈·실측 예시를 더해 받는다. 동결 섹션은 현재 것으로 되돌려 붙이고 길이
상한은 똑같이 건다. **Writer 표본 사이의 `H_set` 차이(judge07 0.5918/0.5764, judge08
0.6027/0.5932)가 편집 하나의 효과(±0.01)보다 크다** — 그 분산을 후보로 쓰기 위해서다.
`--generate-v0` 런에서만 된다.

왜 여러 개인가. judge03~08 에서 판정까지 간 개정 9건 중 채택은 1건이었다. 후보 하나에
이터레이션 전체 채점($3)을 거는 것보다 셋을 50문장에서 재고(후보당 약 $1) 가장 나은 것만
끝까지 재는 쪽이 같은 돈으로 채택 기회를 늘린다. 이터당 비용은 약 $3 에서 $5 로 는다.

### 5.7 실측 라벨 예시

`--labeled-examples` 이면 사례 문장마다 실측 라벨을 순위 백분위(0~100)로 채운
`Input: … / Output: …` 쌍을 만들어 PE 에 `labeled_examples` 로 준다. PE 는 편집에
`"labeled_example": "<사례 id>"` 를 쓰면 코드(`resolve_labeled_examples`)가 그 쌍을 그대로
붙인다. 없는 id 를 가리킨 편집은 그것만 건너뛴다.

**왜 필요한가.** judge03~08 에서 PE 는 예시(`E`)를 한 번도 고치지 않고 원칙(`C`)만 늘렸다.
원칙은 모든 자리에 걸려 다른 구간에서 부작용을 냈다 — judge08 iter 2 의 부검은 "더 일찍
자르라"는 원칙이 짧은 조각 구간 전부를 떨어뜨렸다고 진단했다. 실측 예시는 순위 자체를 보여
주고 사례 문장에만 걸린다. 유일한 채택(judge04 iter 1)도 추상 원칙이 아니라 구체적인 점검
질문이었다. judge09 의 채택(iter 2)은 손으로 쓴 예시 셋을 실측 예시로 갈아끼운 것이다.

예시로 들어간 문장을 그 문장에서 채점하면 안 되므로 판정에서 뺀다(§4).

### 5.8 개정 부검

채점한 개정마다 어디가 어떻게 움직였는지 남긴다. 추가 채점이 없으므로 계산 비용은 0 이고,
LLM 호출만 이터당 하나 는다.

- `revision_diagnosis` 가 (문장, k) 짝마다 H_set 변화를 재서 **지연 구간별 평균 Δ**,
  나빠진·좋아진 짝 수, 가장 많이 움직인 다섯 짝씩(절단 전후를 `‖` 로 표시)을 낸다.
- 부검 에이전트가 그 표를 근거로 `why`(무엇이 달라져 값이 움직였나) / `blamed`(어느 단위) /
  `lesson`(다음 개정이 지킬 것)을 쓴다. 새 규칙은 여기서 제안하지 않는다 — Critic 몫이다.
- 결과는 이력 항목의 `diagnosis` 로 들어가 **다음 이터의 Critic 입력과 PE 이력에 함께 실린다.**

없을 때 무슨 일이 났는지가 이 장치의 이유다. 이력에 평균 Δ 하나만 있으면 Critic 은 직전
개정이 어디서 무너졌는지 모르고 같은 사례를 보고 같은 방향을 되풀이한다 — judge05 는 같은
판정 블록 병합이 세 이터 연속 나왔고, judge07 은 다섯 이터가 같은 사례 12개를 봤다.

## 6. 통계 절차

### 6.1 채택 관문

판정 집합에서 **쌍체 부트스트랩**(2,000회)의 95% 신뢰구간 하한으로 가른다.

| CI 하한 | 판정 |
|---|---|
| > 0.005 | 채택 |
| 0 < lo ≤ 0.005 | 경계선 — 신선한 캐시로 한 번 더 채점하고, 살아남으면 채택 |
| ≤ 0 | 기각, 현재 프롬프트 유지 (유망하면 아래) |

**짝은 (문장, k)**, 재추출 단위는 **문장**이다. 같은 문장의 k 들은 같은 점수 벡터에서
나오므로 독립이 아니다 — 짝 단위로 재추출하면 CI 가 실제보다 좁아져 아무것도 아닌 개정이
통과한다. dev-A 는 1,236 짝 / 150 클러스터, test-A 는 1,651 짝 / 200 클러스터다.

**왜 1 se 문턱을 버렸나.** 종전 관문은 `Δ > 1 se` 였는데 **같은 프롬프트를 다시 채점만 해도**
Δ 가 +0.023 ± 0.017 로 그 문턱을 넘었다(run22 실측, k=1). 언덕 오르기 자체는 유지한다 —
사례가 현재 프롬프트의 실패에서 나와야 개정이 누적되기 때문이다. 대신 짝을 문장에서
(문장, k)로 늘려 CI 를 좁히고, 문턱을 CI 하한으로 올리고, 경계선은 재채점으로 확인한다.

**유망한 기각은 문장을 더 재서 다시 가른다**(`--confirm-dev-b`). 평균 > 0.005 이고 하한 >
−0.01 인 개정은 dev-B 265문장을 더 재서 판정 집합과 합산한 쌍체 부트스트랩(문장 415)의
하한으로 다시 판정한다. 현재 프롬프트의 dev-B 값은 체크포인트에 있으면 그것을 쓰고, 없으면
재서 체크포인트로 남긴다. 유망한 개정 하나에 약 $5 든다.

**문턱을 낮추는 게 아니라 표본을 늘리는 것이다.** dev-A 150문장의 쌍체 CI 반폭이 약 0.015 라
+0.01 짜리 진짜 이득은 원래 통과할 수 없다. judge09 iter 1 은 +0.0105 [−0.0045, +0.0259] 로
기각됐고, 같은 개정을 문장 415 로 다시 재니 +0.0080 [+0.0011, +0.0158] 로 통과했다(반폭
0.015 → 0.007).

### 6.2 채점 잡음

분절기가 비결정론적이다. `gpt-5-mini` 는 `temperature=0` 을 400 으로 거부하고, `gpt-5.4-mini`
는 사고를 끈 상태에서만 받아주는데 그 상태로는 태그를 필요량의 1/3 밖에 안 찍는다. **실사용
설정에서 결정론은 얻을 수 없다.**

- 같은 v0 를 dev 에서 두 번 재면 남긴 경계의 **28%** 가 옮겨간다(run22).
- 개정이 만드는 churn 이 30~37% 라, 한 번 채점으로는 개정 효과와 잡음이 구분되지 않는다.

그래서 `k_samples=3` — 같은 문장을 세 번 채점하고 **순위**를 평균한다(`mean_rank_scores`).
점수가 아니라 순위인 이유는 샘플마다 절대 눈금이 달라도 순위는 같은 자이기 때문이다.
평균 순위가 같은 자리는 정규화한 원점수 평균을 백분위 한 칸의 0.01배로 더해 가른다 — 순위가
다르면 절대 못 뒤집고 동점일 때만 작동한다. 그대로 두면 절단기가 위치(앞쪽 우선)로 정해
편향이 된다(run22 캐시 두 샘플로 잰 tie_rate 0.38).

### 6.3 체크포인트와 롤백

2 이터마다 dev-B 265문장으로 감사한다.

- 그 이터의 개정이 반려·기각돼도 돈다. 반려 경로가 체크포인트를 건너뛰던 때 judge03·04 는
  dev-B 를 한 번도 못 쟀다.
- 프롬프트가 직전 체크포인트와 같으면 다시 재지 않는다.
- 롤백은 직전 체크포인트와 (문장, k) 짝으로 비교해 **CI 상한이 0 아래일 때만** 한다.
  점 비교였던 judge05 는 같은 프롬프트를 캐시로 다시 쟀는데 0.5440 → 0.5416 으로 흔들려
  롤백을 냈다.

**그 흔들림은 QE 가 아니라 번역에서 온다.** CometKiwi 는 같은 입력 600건을 다시 채점하거나
순서를 섞어도 차이가 0 이고 배치 크기를 바꿔도 최대 6e-6 이다. madlad 는 같은 묶음을 두 번
번역해도 120건 중 2건이 달랐다. 번역 캐시가 20건마다만 쓰이던 때는 프로세스가 죽으면 남은
번역이 사라져 다음 실행에서 다른 문장으로 다시 만들어졌다. 지금은 채점이 끝날 때마다
플러시한다.

**조각 번역 캐시의 키는 조각 원문이어야 한다.** 2026-09-15 까지는 `(문장 번호, 시작, 끝)` 이
키여서, 한 채점기로 dev-A 를 잰 뒤 dev-B·test 를 재면 같은 번호·구간의 **다른 문장**이 앞
문장의 조각 번역을 받았다. dev-A 는 늘 먼저 재서 멀쩡했고 dev-B·test 만 오염됐다 — judge08
최종 test 0.4919(dev-A 0.6027)에 오라클까지 0.5595(dev-A 0.6744)로 같이 내려앉은 것이 그
흔적이다. 그 이전에 잰 체크포인트·최종 test 값은 쓰지 않는다.

쪽을 적었다 — 크래시·재시작으로 스냅샷을 못 남긴 실행의 지출이 기록 합계에서 빠진다.

**비용의 98% 가 분절 호출의 사고 토큰이다.** 줄이는 레버는 모델 > `--seg-reasoning-effort` >
`--batch-size` 순이고 프롬프트 길이는 무의미하다. 프롬프트 캐싱은 걸리지 않는다
(`cached_tokens: 0`) — 입력 토큰 전액 과금이다.

### 7.6 재개와 기록

몇 시간짜리 런이라 끊기면 다시 도는 값이 크다.

- 이터 경계마다 `state.json` 에 완료 이터 수, 현재 프롬프트, 시도 이력, 체크포인트, 시작
  길이, 단위 출처표, 런 누적 지출을 쓴다. 임시 파일에 쓰고 이름을 바꾸므로 쓰는 도중에
  죽어도 직전 상태가 남는다.
- 도중에 끊긴 이터는 Critic 부터 다시 한다 — PE 가 비결정론이라 같은 후보가 안 나오므로
  그 이터의 채점 비용은 한 번 더 든다.
- `--budget` 은 런 전체 상한이다. 앞선 실행 지출은 `iter_*/metrics.json` 의
  `run_total_cost` 와 `state.json` 중 최댓값으로 잡아 뺀다.
- `--resume` 은 이미 써 둔 v0 후보 파일을 Writer 를 다시 부르지 않고 그대로 채점한다
  (분절 캐시 적중이라 공짜다).
- 단계별 소요는 `timing.json` 에 남는다(사례 선정 / Critic / PE / 선별 / 후보 채점 /
  dev-B 확인 / 부검).

## 8. 검토하고 버린 것 (논문에서 "왜 이것이 아닌가"로 쓸 수 있는 것)

| 후보 | 왜 버렸나 | 실측 |
|---|---|---|
| 구문 경계 정렬률 (SASST 방식) | 언어별 파서가 필요해 "언어 지식은 데이터로만" 원칙과 충돌 | SASST 82% vs 고정길이 23% — 축 자체는 유효 |
| MU / prefix-consistency 라벨 | 판정 기준이 offline 번역의 어순이라 **단조성을 전제한다** — "나쁜 경계"와 "offline 이 어순을 바꿈"을 못 가른다 | 표면형 `chrf` 고정점 1.1% → 함의로 바꾸면 25.1% |
| 경계 단위 `consistency` (합본 vs 전체번역 양방향 NLI) | 타깃 간 문장 내 순위상관 **0.086**(잡음). 복구가 실패를 가린다 | 주 작동점 T=6·8 에서 현행 대비 유의하게 나쁨. `cons` 가 고른 자리의 contra 평균이 반대쪽의 5배 |
| 참조 없는 QE 로 조기 방출 검출 | 조각 원문·조각 번역만 보므로 **미래에 의한 반박을 원리적으로 못 본다** | 케이스 5건 중 4건 순위 위반 — 조기 완성을 오히려 보상 |
| LLM 판정자를 목적함수에 | 오판 1건이 문장 평균을 0.02 움직이는데 검출 대상이 0.003 규모 | 판정자는 조향에만 쓴다 |
| 임베딩 코사인으로 NLI 대체 | 관문 통과 0/4. 신호가 대부분 음수 — 잘못 자른 방출이 안전한 방출보다 전체번역에 *더* 가깝다 | 원인은 부정 맹목이 아니라 참여자 뒤바뀜(재서술 0.992 < 역할 교환 0.996) |
| 학습 헤드를 얹은 bi-encoder | 코사인보다 크게 낫지만 교차 인코더에 모순 오류율 11배로 진다 | MNLI 3-way 0.440 → 0.719, 교차 인코더 0.916 |
| 표현 급변점을 경계로 | **문장을 하나도 안 보는 위치 사전확률**이 전 항목에서 더 높다 | raw AUC 0.61~0.81 vs 위치 사전확률 0.685~0.864, 교란 제거 후 0.42~0.54 |
| MiniCheck | 어순 단조화를 벌한다 — COMET consistency 를 버린 이유와 같은 편향 | `benign_reordered` 0.7895 vs `benign_incomplete` 0.0938 |
| `rank_contra_gap` 을 최적화 목표로 | 안전한 경계만 찍는 프롬프트는 gap≈0 인데 품질이 좋다. 게다가 순위가 실제로 일하는 큰 T 에서 정의역이 사라진다 | T=8 에서 측정 가능 2/100, T=12 에서 0/100 |
| 부분 순위 (상위 N 개만 번호) | 정렬 생략이 평가 생략이 아니다 — 상위 5개를 고르려면 11개를 다 평가해야 한다 | 사고 토큰 6,884 → 8,033/콜로 **17% 증가** |

**다시 볼 값어치가 있는 하나**: `retrans` premise (전체번역 대신 다음 조각까지의 소스
재번역). SNR 5.88 로 현행 5.74 보다 높고 바닥이 더 낮고 평탄하며, 오라클이 필요 없어 참조
오염이 구조적으로 사라진다. 비용은 경계당 번역 1회. 축이 달라져 기존 런과 비교가 끊기는
것만이 미채택 사유다.

## 9. 한계와 미해결

논문 각주로 옮길 것들이다.

1. **중첩 제약 하 최적을 아직 안 쟀다.** 이 값이 루프의 진짜 목표선인데 없다. T별 최적
   집합이 서로 중첩인 문장이 42%뿐이라 탐색 최적 0.7919 는 점수 벡터 하나로 도달 불가능하다.
2. **채택률이 낮다.** 판정까지 간 개정 15건 중 2건이고, 둘 다 CI 하한이 +0.001 안쪽인
   경계선이었다. 프롬프트 조향의 효과 크기가 측정 잡음과 같은 자릿수(0.006 vs se 0.008)라는
   구조적 사실이 배경이다. 실측에서 **결정론적 코드 변경이 프롬프트 조향을 일관되게 이겼다**
   (후보 풀 확대 +0.0130, 절단 간격 +0.0102 vs 프롬프트 조향 수동 3회·자동 3회 전부 ~0 또는
   음수).
3. **스트리밍 제약은 이 루프 밖이다.** 여기 정책은 문장 전체를 보고 순위를 매기는데 실제
   SEG 헤드는 들은 데까지만 본다. 라벨은 그대로 쓰되 입력과 결정 규칙(전역 상위 k → 임계값)이
   달라진다. 별도 트랙이다.
4. **집합 수준 오류를 다루지 않는다.** 경계별로는 좋은 자리인데 조합에서 틀린 것을 말한다.
   목표가 그리디 오라클이면 그리디가 경계별 값 순으로 고르므로 이런 사례가 거의 안 나온다.
   목표를 집합 탐색 최적(`--target-sets`)으로 두면 그 몫이 드러나는데, 그걸 판단 기준 문장으로
   표현할 수 있는지는 모른다. 못 하면 프롬프트가 아니라 정책 형태(집합 인식 디코딩)로 가야 한다.
5. **범용성 주장 금지.** 문장만 미출현이고 코퍼스·레지스터는 그대로다. 결과 서술을 "FLEURS
   도메인 내"로 한정한다. 도메인 전이가 필요하면 NTREX-128 표본 200 을 같은 프로토콜로 추가한다.
6. **타깃이 미출현이 아니다.** 평가 타깃 언어(zh/ja/de/es)가 루프 목적함수에 들어가 있었다.
7. **FLEURS 는 FLoRes 파생 공개 데이터**라 상용·공개 번역기가 학습에 봤을 수 있다. 세 조건에
   동일하게 작용하므로 상대 비교는 유지되지만 절대값의 타 논문 비교엔 각주가 필요하다.
8. **입력 잡음 미검증.** 실제 ASR 출력은 커밋 경계에서 가짜 마침표를 만든다(실측 mode2
   6.9어절당 1개, mode4 45어절당 1개). 여기 평가는 정서법이 깨끗한 텍스트 입력이다.
9. **평가와 운영의 문맥 설정이 다르다.** 평가는 조각 번역에 앞 조각 원문을 문맥으로 붙이고
   (`use_context=True`), 운영 서버 기본은 독립 번역이다. 복구 능력이 평가 쪽에서 더 크다.
10. **런 간 비교 가능성이 네 번 끊겼다** — 목적함수 교체(v1→v2), contradiction 집계 방식
    변경, 번역 백엔드 교체(gtx→v2, 재번역 대조 일치 0/18), 순위 태그 → 점수 태그(2026-09-10).
    오래된 런의 숫자를 같은 표에 올리기 전에 확인해야 한다.
11. **2026-09-15 이전의 dev-B·test 값은 못 쓴다.** 조각 번역 캐시가 문장 번호로 키를 잡아
    두 번째로 채점하는 분할이 오염됐다(§6.3). 판정에 쓰는 dev-A 는 늘 먼저 재서 영향이 없고,
    체크포인트·유망 확인·최종 test 만 해당한다.

for sp in dev test train; do

.venv/bin/python -u -m core.meaning_segmentator.tools.autoseg_en2x.run24.probe.make_run25

tmux new-session -d -s judgeNN -c <저장소> \
