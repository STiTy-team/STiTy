# loop_judge — 판단형 프롬프트 루프 설계

`loop_distill` 을 대체하는 두 번째 루프. 같은 인프라(Gateway, 캐시, `evaluate`, 부트스트랩)를
쓰고 **사례·Critic 출력·개정 위치·채택 관문 넷을 바꾼다.** 왜 바꾸는지는 실측으로 다음과 같다.

| 실측 | 값 | 함의 |
|---|---|---|
| 표면형 규칙 프롬프트(v0) → 판단형(minimal) | dev overlap 0.4767 → 0.5485 | 규칙 채굴이 아니라 판단 기준이 이긴다 |
| 판단형 프롬프트끼리 | 0.477~0.483 (구별 안 됨) | 문구 손질로는 더 안 오른다. 루프가 필요하다 |
| 같은 프롬프트 재채점 Δ | +0.023 ± 0.017 (k=1) | 1 se 문턱 언덕 오르기는 잡음의 위쪽 꼬리를 담는다 |
| 규칙 하나가 닿는 경계 | dev 3,399 중 3~5 | 토큰 관문은 20% 교란에 묻힌다 |

## 무엇을 맞히나

라벨은 `cohesion × (1 − contra)` (→ [AUTOSEG_DETAILS.md](AUTOSEG_DETAILS.md) 의 셋째 축 절).
정책은 원문만 읽고 경계마다 점수를 낸다. T마다 상위 k개가 절단이 된다.

세 기준선을 같은 자(`H_set`)로 잰다. test 100문장 gold(COMET-DA, 3타깃) 값을 괄호에 적는다.

```
무분절                                    (0.8770)   T=∞ 참고선
집합 탐색 최적 — 오프라인 교사만 도달        (0.7919)
중첩 제약 하 최적 — 점수 벡터 하나의 천장     (미측정)   ← 루프의 진짜 목표선
그리디 오라클 — 경계별 H 상위 k             (0.7780)
정책 minimal_tgt                          (0.7686)   ← 현재 위치
```

`H_set(S) = CometKiwi(원문 전체, 조각 번역 이어붙임) × (1 − max contra(S))`.
참조 번역이 필요 없다. 정책·오라클·탐색이 전부 이 자로 재진다.

## 이터레이션

```
1. 현재 프롬프트로 dev-A 채점 (k=3) → T마다 절단 → 조각 번역(캐시) → H_set
2. 사례 선정: 오라클 대비 H_set 차이가 큰 (문장,T) 상위 N
3. Critic: 사례를 읽고 판단 기준 수정안 또는 예시 쌍을 낸다
4. PE: [Core Principles] 의 질문 또는 [Examples] 를 고쳐 후보를 만든다
5. 후보 채점 → 쌍체 부트스트랩 (짝 = 문장 × T = 860)
     CI 하한 > 0.005      → 채택
     0 < CI 하한 ≤ 0.005  → 신선한 캐시로 한 번 더 재고, 살아남으면 채택
     CI 하한 ≤ 0          → 기각, 현재 프롬프트 유지
6. 2 이터마다 dev-B 체크포인트. 나빠졌으면 마지막 확인 지점으로 롤백
7. 반복

끝: 마지막 채택본을 dev-B 로 확인 → test 는 한 번
```

**언덕 오르기를 쓰되 문턱을 올린다.** 사례가 현재 프롬프트의 실패에서 나와야 개정이
누적되므로 언덕 오르기가 맞다. 다만 종전의 1 se 문턱은 재채점 잡음(+0.023 ± 0.017)이
그냥 넘는 크기였다. 짝을 문장에서 (문장,T)로 늘려 CI 를 좁히고, 문턱을 CI 하한 > 0 으로
올리고, 경계선 채택은 재채점으로 확인한다.

## 사례가 담는 것

스칼라 차이가 아니라 **반사실 쌍**을 준다.

```
문장 #37, T=6      정책 H_set 0.71 / 오라클 0.79  (−0.08)
정책 절단   … the company, ‖ which had lost money for years, ‖ finally turned a profit
오라클 절단 … the company, which had lost money for years, ‖ finally turned ‖ a profit
정책만 고른 자리 A("company," 뒤)  경계별 H 0.79 (상위 20%)  coh 0.81  contra 0.02
오라클만 고른 자리 B("turned" 뒤)   경계별 H 0.52 (하위 40%)
양쪽 절단의 조각 번역 (zh/ja/de)
```

**사례는 지연 구간마다 고르게, 문장당 하나씩 뽑는다** (`pick_cases`). 손해 상위만 뽑으면 한
구간에 몰린다. judge05 는 12개가 전부 평균 조각 2~3.5어절에 손해 0.67~0.80 이었고, 모순 절단
하나로 집합이 0 이 된 경우뿐이었다. Critic 은 그걸 "뒤집힐 수 있는 자리를 더 피하라" 로
일반화했고, 넣을 때마다 짧은 조각 구간이 떨어졌다(iter 2~5 전부 기각, Δ −0.014 ~ −0.038).

사례에는 `latency_bin`(평균 조각 길이 구간)과 `contra_kill`(정책 절단 하나의 contra 가 0.5
이상이라 집합이 0 이 됐고 목표 쪽은 그렇지 않음)이 붙는다. Critic 지시문은 `contra_kill` 사례를
절단 전반에 대한 경고로 바꾸지 말라고, 짧은 구간에서는 좋은 절단집합이 원래 촘촘하다고 알린다.

## Critic 계약

입력: 위 사례 묶음 + 현재 프롬프트.
출력 JSON. **토큰 조건(`left_last`/`right_first`)을 받지 않는다.**

```json
{"findings": [
  {"diagnosis": "무엇을 오판했나 — 한 문장",
   "edit": {"where": "core_principles" | "examples",
            "action": "add" | "replace",
            "target": "고칠 줄의 첫 몇 단어 (replace 일 때)",
            "text": "새 문장 또는 예시 쌍"},
   "cases": ["문장 id ..."]}]}
```

`diagnosis` 는 판단의 종류를 말해야 한다 — "삽입절 뒤 쉼표를 완결로 오해", "뒤 조각을
안 봄" 처럼. 토큰 목록은 반려한다.

## PE 계약

`[Core Principles]` 의 질문과 `[Examples]` 만 고친다. `[Scoring Rules]` 와 `[Output Rules]`
는 동결이다.

- `[Scoring Rules]` 는 **측정 절차를 서술하는 유일한 자리**다 — cohesion·contra 가 무엇이고
  어떻게 곱하는지, 그리고 결합식과 순위 규칙. Writer 가 v0 를 만들 때 쓴다.
- `[Output Rules]` 는 출력 형식만 두고, 점수의 뜻은 `[Scoring Rules]` 를 가리킨다
  (`agents_distill.output_rules(..., meaning_in_scoring_rules=True)`). 두 곳에 측정을 쓰면 라벨을
  바꿀 때 한쪽만 고쳐져 한 프롬프트 안에 서로 다른 목표 설명이 남는다.

### 분할 — 2분할 런(run25), 3분할 런(run26), 4분할 런(run27)

소스 런의 `data/test_a.json` 이 있으면 3분할로 돌고, `data/test.json` 까지 있으면 최종 표를 거기서 잰다.

| 분할 | 2분할 (run25) | 3분할 (run26) | 4분할 (run27) |
|---|---|---|---|
| 사례·실측 예시 출처 | dev-A 150 | **train 200** (현재 프롬프트를 train 에서 채점, 프롬프트가 바뀐 이터에만) | 같음 |
| 채택 판정 (선별 50 + 본채점) | dev-A 150 | **test-A 200** | 같음 |
| 체크포인트·유망 확인 | dev-B 265 (dev 나머지 + train) | **test-B 200** (dev 나머지 65 + 옛 test 100 + 추가 35) | 같음 |
| 최종 표 (채택본 vs v0) | test 100 | test-B 가 겸함 — 홀드아웃 없음 | **test 200** — 어느 판정에도 안 쓴 문장 |

- 왜 갈랐나: 2분할에서는 실측 예시(사례 문장 + 라벨 순위)가 프롬프트에 들어간 채 같은 문장에서
  채점됐다. judge09 iter 2 는 dev-A Δ +0.0105 중 +0.006 이 예시 3문장 몫이었다(예시 제외
  +0.0044 [−0.0079, +0.0161]). 3분할에서는 출처(train)와 판정(test-A)이 겹치지 않는다. 방어로
  `example_sentences()` 가 프롬프트 [Examples] 에 들어간 문장을 어느 분할에서든 판정에서 뺀다.
- run26 만드는 법: `tools/autoseg_en2x/run24/probe/make_run26.py` 머리말. run27 은
  `tools/autoseg_en2x/run27/make_run27.py` — run26 분할에 분할 밖 285문장(프로파일 재료 20 제외)에서
  시드로 뽑은 test 200 을 더하고 같은 절차로 라벨을 만든다(`make_run27.sh` 가 체인).

### 개정 후보 여러 개와 선별 (`--pe-candidates`, `--screen-n`)

`--pe-candidates N` (기본 1) 이 2 이상이면 이터마다 PE 를 N 번 불러 서로 다른 개정을 받는다. 두
번째부터는 앞선 후보의 편집 요약을 `sibling_candidates` 로 넘겨 같은 방향을 피하게 한다. 후보는
판정 집합에서 **이터마다 시드로 돌려 뽑은** `--screen-n` 문장(기본 50, `screen_indices`)에서 먼저
재고, 현재 프롬프트와의 짝 부트스트랩 Δ 평균이 가장
높은 후보만 dev-A 전체로 본채점한다. 선별에 쓴 문장은 분절 캐시에 남아 본채점에서 다시 돈이 들지
않는다. 선별에서 진 후보는 `screened_out` 으로 이력에 남아 PE 가 같은 방향을 또 내지 않게 한다.
산출물: `iter_NN/candidate_J.txt`, `screen.json`. 후보들의 분절(API 대기)은 스레드로 동시에 하고
번역·QE(GPU)만 차례로 한다 — 선별 한 후보에 23분이 걸렸는데(judge08 iter 3) 대부분 API 왕복
대기라 겹치면 셋이 그 시간에 끝난다. 표본별 분절 캐시는 `JsonCache.shared` 로 경로당 하나만 둔다
(스레드마다 인스턴스를 만들면 서로의 항목을 모른 채 같은 파일을 덮어쓴다).

`--screen-skip` 이면 선별 최고 후보의 Δ 평균이 0 이하일 때 본채점 없이 기각한다. 부검은 선별
문장으로 하고 `regression.json` 에 `screened_only` 를 남긴다. 본채점($2, 30분)을 아껴 같은 예산과
시간에 시도 횟수를 늘리는 쪽이다.

`--candidate-roles free,examples_only,single_small` 이면 후보 j 는 `roles[j % len]` 의 제약을 받는다
(`constraint` 로 PE 에 알리고, `enforce_role` 이 어긴 편집을 뺀다). `examples_only` 는 [Examples]
단위만, `single_small` 은 편집 하나·새 본문 60단어 이내. 같은 이터에 보폭이 다른 후보를 섞어 두기
위해서다 — 원칙을 통째로 갈아끼운 후보는 매번 전 구간을 흔들었다(judge08 iter 2~4 부검).
`rewrite` 는 편집이 아니라 Writer 가 v0 때 재료(프로파일·실측 사실·표본 문장·[Output Rules])에
현재 프롬프트·Critic 소견·부검 교훈·실측 예시를 더해 [Core Principles]·[Examples] 를 새로 쓴다.
동결 섹션은 현재 것으로 되돌려 붙이고, 길이 상한은 똑같이 건다. 초안이 길이만 넘으면 Writer 를
다시 부르지 않는다 — 통째로 다시 쓰므로 길이가 손을 떠난다(judge10 iter 1: 8074자 → 재시도
8104자). 대신 초안을 편집 단위로 쪼개 PE 에게 주고 초과량만큼 줄이게 한다(`shorten_user`).
한 패스에 15% 남짓만 깎이므로(judge10 iter 2: 9748 → 8339) 맞을 때까지 최대 3번 반복하고,
축소 패스의 insert 편집은 코드가 뺀다(같은 곳에서 삭제 −1596 에 예시 추가 +262).
Writer 표본 사이의 H_set 차이
(judge07 0.5918/0.5764, judge08 0.6027/0.5932)가 편집 하나의 효과보다 커서, 그 분산을 후보로
쓰기 위해서다. `--generate-v0` 런에서만 된다.

선별 문장을 늘 같은 앞 50으로 두면 거기에 맞는 후보가 이터마다 살아남고, 그 50이 든 본판정 Δ 도
그만큼 부풀려진다. `screen.json` 에 그 이터의 인덱스가 남는다. 같은 이유로 **v0 후보도 판정
집합이 아니라 사례 집합(3분할: train)에서 고른다** — 판정 집합에서 고른 v0 는 판정값이 낙관
편향이라 이후 개정이 부풀려진 기준선을 넘어야 한다.

PE 입력은 편집 단위(`units`)·소견·`fixed_sections`([Role]·[Scoring Rules])·이력 요약
(`history_brief`: 이터·후보·채택 여부·Δ 평균과 하한·편집·교훈)·길이 실측이다. 프롬프트 전체와
이력 전체는 주지 않는다 — 단위가 본문을 이미 담고, 전체 이력은 4이터에 20KB 였다.

### 유망한 기각의 dev-B 확인 (`--confirm-dev-b`)

dev-A 에서 기각됐지만 평균 > 0.005 이고 하한 > −0.01 인 개정(`promising`)은 dev-B 265문장을 더
재서 dev-A 와 합산한 쌍체 부트스트랩(문장 415, 클러스터는 문장) 하한으로 다시 가른다. 현재
프롬프트의 dev-B 값은 체크포인트에 있으면 그걸 쓰고, 없으면 재서 체크포인트로 남긴다. 유망한
개정 하나에 약 $5. `gain` 에 `dev_a`/`dev_b`/`pooled` 가 함께 남는다.

- 왜: dev-A 150문장의 쌍체 CI 반폭이 약 0.015 라 +0.01 짜리 진짜 이득은 통과할 수 없다.
  judge09 iter 1 은 +0.0105 [−0.0045, +0.0259] 로 기각됐다. 문장을 415 로 늘리면 반폭이 약
  0.009 가 된다. 문턱을 낮추는 게 아니라 표본을 늘리는 것이다.

### 실측 라벨 예시 (`--labeled-examples`)

사례 문장마다 실측 라벨을 순위 백분위(0~100)로 채운 `Input: … / Output: …` 쌍을 만들어 PE 에
`labeled_examples` 로 준다. PE 는 편집에 `"labeled_example": "<사례 id>"` 를 쓰면 코드가 그 쌍을
그대로 붙인다 (`resolve_labeled_examples`). 없는 id 는 그 편집만 건너뛴다.

- 왜: judge03~08 에서 PE 는 예시(E)를 한 번도 고치지 않고 원칙(C)만 늘렸고, 원칙은 모든 자리에
  걸려 다른 구간에서 부작용을 냈다(iter 2 부검: "더 일찍 자르라" 는 원칙이 짧은 조각 구간 전부를
  떨어뜨림). 실측 예시는 순위 자체를 보여 주고, 사례 문장에만 걸린다. 유일한 채택(judge04 iter1)
  도 추상 원칙이 아니라 구체적 점검 질문이었다.

- 왜: judge03~08 에서 끝까지 잰 개정 9건 중 채택은 1건이었다. 후보 하나에 이터레이션 전체
  채점($3)을 거는 것보다 셋을 50문장에서 재고($1씩) 가장 나은 것만 끝까지 재는 쪽이 같은 돈으로
  채택 기회를 늘린다. 이터당 비용은 약 $3 에서 $5 로 는다.

### 프롬프트 골격 — 다섯 섹션

`[Role] [Core Principles] [Scoring Rules] [Output Rules] [Examples]` (`agents_judge.JUDGE_SECTIONS`).
distill 의 여섯 섹션에서 **[Decision Procedure] 를 뺐다**(2026-09-15). judge09 v0 에서 그 절은
[Core Principles] 의 두 판단(contra·cohesion)을 순서로 다시 쓴 것에 영어 절 구조 힌트를 보탠
것이었고, 순위 규칙(마커마다 다른 정수·넓은 범위)은 코드가 만드는 [Output Rules] 에 이미 있다.
PE 는 원칙만 고치므로 절차의 옛 힌트가 개정과 어긋난 채 남는 것이 문제였다. 골격 검사는 이 절이
있으면 "허용하지 않는 섹션" 으로 반려한다. PE 가 고치는 곳은 [Core Principles]·[Examples],
동결은 [Scoring Rules]·[Output Rules], [Role] 은 손대지 않는다.

### 채점기 조각 번역 캐시는 조각 원문으로 키를 잡는다

`HsetScorer` 는 조각 번역을 `{타깃: {조각 원문: 번역}}` 으로 캐시한다(`piece()`). 2026-09-15 까지는
`(문장 index, 시작, 끝)` 이 키여서, 한 채점기로 dev-A 를 잰 뒤 dev-B·test 를 재면 같은 index·
구간의 다른 문장이 앞 문장의 조각 번역을 받았다. dev-A 는 늘 먼저 재서 멀쩡했고 dev-B·test 만
오염됐다 — judge08 test 0.4919(dev-A 0.6027), test 오라클 0.5595(dev-A 오라클 0.6744). 그
이전 런들의 체크포인트·최종 test 값은 무효다.

PE 개정본의 길이 상한은 **직전 채택본 × (1 + `--growth-per-iter`, 기본 0.10)** 와 **시작 길이 ×
`--growth-ceiling`(기본 1.3)** 중 작은 쪽이다.

- 시작 길이에 고정하면 한 번 채택된 뒤 여유가 사라진다. judge04 는 상한 8,664자에 채택본이
  8,652자라 iter 2~4 가 전부 길이로 반려됐다.
- 증가율만 두면 이터마다 쌓인다(10% × 5이터 = 1.61배). 천장이 그걸 막는다.
- 여유는 글자와 **단어** 로 함께 준다(`size.headroom`: 남은 글자·단어, 원칙 한 줄의 평균 단어
  수, 그 여유가 원칙 몇 개 분량인지). LLM 은 글자 수를 못 세지만 단어 수는 어림한다. judge05~08
  에서 5% 여유(약 500자)는 원칙 하나 크기였는데 PE 가 그걸 몰라 추가만 하고 줄이지 않은 편집이
  초과 6건 중 5건이었다. 되돌릴 때의 초과량도 단어로 함께 준다(`over_by_words`).
- 상한을 넘기려면 **근거로 자리를 만든다.** PE 입력의 단위마다 출처가 붙는다 — 들어온 이터
  (`origin`, v0 또는 채택된 이터), 그 채택에서 잰 Δ 와 하한(`adopted_delta` / `adopted_ci_lo`).
  PE 는 근거 약한 단위(v0 이면서 이번 소견이 지적한 것)부터 갈아끼우고, 이득이 잰 단위는 뜻을
  지킨 채 압축만 한다. 압축은 `"kind": "paraphrase"` 로 표시돼 `pe_edits.json` 에 남는다.
- 출처표는 **한 런 안에서만** 쌓인다. 런은 서로 독립이어야 하므로 앞선 런의 채택본이나 출처를
  다음 런이 물려받지 않는다 — 같은 dev-A 에서 한 선택을 다음 런이 이어받으면 런을 거듭하며
  dev-A 에 맞춰 가고, 런끼리 비교도 할 수 없다. 매 런은 자기 v0 를 생성해서 시작한다.
- 이력의 각 항목에 그 이터의 편집 요약(`edits`: 단위, 바꾸기 전 원문 앞부분, 바꾼 뒤)이 실린다.
  사유·Δ 만 있으면 PE 가 기각된 편집을 알아보지 못한다.
- 압축도 분절기에게는 개정이다. 새 규칙과 같은 후보로 함께 재므로 효과를 따로 가를 수는 없고,
  나빠지면 후보째 기각된다.

**PE 는 프롬프트를 다시 쓰지 않고 편집만 낸다.** 모델은 글자 수를 못 센다(judge01: 8000자
지시에 Writer 10,947자, 상한 9,000 에 PE 9,895자). 초과량을 알려 되돌려도 줄지 않았다(judge03:
다섯 번 중 네 번 실패, 그중 두 번은 더 길어짐). 1만 자를 통째로 다시 쓰는 한 길이는 모델 손을
떠난다.

- PE 입력의 `units` 에 `[Core Principles]` 한 줄(`C1`…)과 `[Examples]` 한 쌍(`E1`…)마다 본문과
  실제 글자 수를 준다. PE 는 `replace` / `delete` / `insert_after` 목록을 돌려준다
  (`C0`·`E0` 뒤에 끼우면 섹션 맨 앞).
- 적용과 길이 계산은 코드(`agents_judge.apply_edits`)가 한다. 나머지 섹션은 구조상 건드릴 수
  없다.
- 모델에게 알리는 길이 목표는 상한의 95%(`soft_target`)이고 검사는 상한 그대로다. 목표와
  상한이 같으면 모델은 늘 1% 안팎 넘겼다(judge08~10 초과 12건 중 5건이 1.2% 이내). 상한이
  천장에 닿아 현재 길이와 같으면 목표도 현재 길이다.
- 적용 결과가 길이만 넘으면 편집별 실측 증감(`size_feedback.your_edits`)과 초과량을 붙여
  **한 번** 되돌린다. 되돌린 뒤에도 반려되면 `후보 j: 반려 — 사유` 로 로그에 남는다.
- 없는 id, 섹션 헤더가 든 본문, 쌍이 아닌 예시, 같은 단위를 두 번 고치는 편집은 **그것만 빼고**
  나머지를 적용한다(`pe_edits.json` 의 `skipped`). 묶음을 통째로 반려하면 멀쩡한 편집까지 버려진다
  — judge07 iter 1 은 편집 넷 중 하나가 없는 id `C7` 을 가리켜 이터 하나를 통째로 날렸다.
  남는 편집이 없거나, 적용 결과가 길이·골격·동결 검사에 걸리거나, 예시가 8개를 넘으면 반려한다.
- 두 차례의 편집·증감·결과 길이는 `iter_NN/pe_edits.json` 에 남는다.

부검이 다음 이터에 닿는 길은 셋이다. Critic 은 `last_revision` 으로 편집·Δ·구간별·`why`·`blamed`·
`lesson` 을 다 받고, PE 는 `history_brief` 로 `lesson`·`why`·`blamed` 와 편집 was/now 를, Writer 는
`lessons` 를 받는다. 말로만 주면 안 닿는다 — judge10 iter 2 는 세 후보 전부 iter 1 부검이 지목한
실측 예시를 다시 넣었고, Critic 은 기각된 개정 본문을 현재 프롬프트에 있는 줄 알고 겨눴다. 그래서
코드가 건다: 기각된 개정 본문에 있던 실측 예시는 `labeled_examples` 에서 뺀다(`exclude_used_examples`),
Critic 의 replace 대상이 현재 프롬프트에 없으면 버린다(`clean_findings(_, prompt)`). 부검의 `blamed`
는 그 이터 후보의 단위 id 라 다음 이터엔 다른 단위를 가리키므로 본문 앞부분을 붙여 이력에 넣는다
(`blamed_with_text`). 기각된 rewrite 후보는 편집 목록이 비어 changelog 를 대신 남긴다.

**사례는 이미 보인 문장을 채택될 때까지 누적해서 빼고 뽑는다** (`pick_cases(exclude=…)`). 채택이
없으면 프롬프트도 손해 순위도 그대로라 같은 12문장이 또 뽑히고(judge10 iter 1·2 동일) Critic 은 같은
finding 을 되풀이했다. 직전 이터만 빼면 두 이터 주기로 돌아온다(judge11 iter 1 = iter 3). 채택되면
손해 순위가 새로 생기므로 비운다.

**v0 의 [Examples] 는 Writer 가 짓지 않는다.** train 에서 길이 분위수 자리의 문장 4개를 골라
(`pick_example_ids`) 실측 라벨 백분위로 채운 쌍을 코드가 붙인다(`examples_section`). judge10 v0 의
예시 셋은 Writer 가 점수를 지어낸 것이었다. Writer 에게는 [Core Principles] 를 6~10줄·한 줄 60단어
이내로 쓰게 한다 — judge10 v0 는 원칙이 4단위, 그중 둘이 1,000자라 PE 편집이 통째 재작성이 됐다.
[Scoring Rules] 에는 "곱을 100배해 반올림" 같은 산술 변환을 쓰지 않게 한다 — "서로 다른 정수, 전
범위" 와 모순이었다. Profiler 는 언어 서술만 하고 분절 전략·지연 조언은 내지 않는다 — "동사구가
끝날 때까지 기다려라" 가 v0 를 긴 조각 쪽으로 기울였다. 프로파일은 토큰 목록이 아니라 장치 이름
(괄호에 예시 둘까지)으로 쓰게 한다 — Writer 에게는 토큰 규칙을 금지하면서 재료가 토큰 목록이었다.

Critic 은 근거에 사례 id 를 나열하고 그 길이를 개수로 삼는다(judge10 iter 2: 사례 12개에 "13개 중
10개"). Postmortem 은 `by_bin`·`n_worse`/`n_better` 로 판단하고 최악 5쌍은 예시로만 쓴다(judge10
iter 1: 쌍 하나 Δ −0.79 가 lesson 이 됐다). PE 후보 j 는 finding[j % n] 을 `primary_finding` 으로
받아 먼저 다룬다 — 후보 셋이 같은 finding 으로 수렴했다. 같은 이터에서 앞 후보가 넣은 실측
예시는 뒤 후보에게 내놓지 않고 써도 코드가 뺀다, 본문이 같은 후보는 선별에서 뺀다
(`dedupe_candidates`) — judge12 iter 1 은 후보 넷 중 셋이 같은 예시(E4 → en_us_738)를 넣었고
둘은 본문까지 같았다.

**선별 평균이 양수인 후보는 `--full-score-max` 개까지 전부 본채점한다.** judge12 는 5이터 전부
후보 CI(±0.025)가 겹쳐 선별 1등이 잡음으로 정해졌고, 1등 셋이 본채점에서 전부 음수였다
(사이드 채점한 2등도 음수). 본채점한 것 중 CI 하한이 가장 높은 후보가 판정으로 간다. 나머지는
`full_scored` 로 이력에 남는다.

**사례는 구간별 손실 몫에 비례해 뽑을 수 있다**(`--case-alloc loss`, 구간마다 최소 1). judge12
v0 의 test-A 손실은 61% 가 ≤3 구간, 26% 가 ≤5 구간이었는데(`loss_by_bin`) 균등 배분은 그 둘에
12개 중 6개만 줬다. 기각된 개정 10건 중 9건이 그 두 구간을 떨어뜨렸다 — 전부 "어디서 자르지
말라" 는 원칙이었다. 같은 표를 Critic·PE 입력(`loss_by_bin`)으로도 준다.

**최종 test 는 채택본이 v0 그대로면 생략한다.** 잴 것이 없다. 체크포인트는 홀드아웃 test 가
생긴 뒤로 `--checkpoint-every 0` 으로 끌 수 있다 — 채택본의 과적합은 최종 test 가 잡는다.

## 개정 부검

채점한 개정마다 **어디가 어떻게 움직였는지** 를 남긴다. 추가 채점이 없으므로 계산 비용은 0 이고,
설명 한 문단을 받는 LLM 호출만 이터당 하나 는다 (`purpose="postmortem"`).

- `revision_diagnosis` 가 (문장, k) 짝마다 H_set 변화를 재서 **지연 구간별 평균 Δ**, 나빠진·좋아진
  짝 수, 가장 많이 움직인 다섯 짝씩(절단 전후를 `‖` 로 표시)을 낸다.
- 그 표를 근거로 부검 에이전트가 `why`(무엇이 달라져 값이 움직였나) / `blamed`(어느 단위) /
  `lesson`(다음 개정이 지킬 것) 을 쓴다. 새 규칙은 여기서 제안하지 않는다 — 그건 Critic 몫이다.
- 결과는 `iter_NN/regression.json` 에 남고, 이력 항목의 `diagnosis` 로 들어가 **다음 이터의 Critic
  입력(`last_revision`)과 PE 이력에 함께 실린다.**

없을 때 무슨 일이 났는지가 이유다. 이력에 평균 Δ 하나만 있으면 Critic 은 직전 개정이 어디서
무너졌는지 모르고, 프롬프트가 안 바뀌면 같은 사례를 보고 같은 방향을 되풀이한다 — judge05 는
같은 판정 블록 병합이 세 이터 연속 나왔고, judge07 은 다섯 이터가 같은 사례 12개를 봤다.

## 최종 test 와 이터 기록

- **최종 test.** 런이 끝나면 채택본과 **v0** 를 test 100문장에서 같은 자로 재고, 그리디 오라클도
  함께 낸다. 지연 구간별 표는 `curve.json`, 한 장 요약은 `final_report.md` 다. v0 를 같이 재야
  "이 런이 실제로 올린 폭" 이 남는다 — dev 는 개정을 고르는 데 이미 소진됐다. `--skip-final` 로
  끈다. 비용은 채택된 개정이 있으면 약 $4, 없으면 약 $2 다.
- **포맷 위반.** 이터마다 `violations.json` 에 규칙별 건수와 문장 id 를 남긴다. 통과율 숫자만
  남기면 1차 통과율이 떨어져도 무엇이 깨졌는지 재현 실험으로만 찾을 수 있다.
- **단계별 시간.** `timing.json` 에 사례 선정·Critic·PE·후보 채점·부검 소요를 남긴다.

## 관문과 가드

| | 무엇 | 비용 |
|---|---|---|
| 채택 | dev-A `H_set` 쌍체 부트스트랩 CI 하한 > 0 (짝 860) | QE 2,000건 ≈ 1분 |
| 가드 | 고른 자리의 소스 contra 평균이 시작점보다 오르면 탈락 | 0 (`probe/contra_at_cuts.py`) |
| 감사 | 체크포인트마다 dev-B gold(COMET-DA) | GPU 6~8분 |
| 형식 | 1차 통과율이 0.9 아래로 내려가면 탈락 | 0 |

체크포인트(`--checkpoint-every`)는 그 이터의 개정이 반려·기각돼도 돈다. 반려 경로가 체크포인트를
건너뛰던 때 judge03·04 는 dev-B 를 한 번도 못 쟀다.

- 프롬프트가 직전 체크포인트와 같으면 다시 재지 않는다.
- 롤백은 직전 체크포인트와 (문장, k) 짝으로 비교해 **CI 상한이 0 아래일 때만** 한다
  (`checkpoint_verdict`). 점 비교였던 judge05 는 같은 프롬프트를 캐시로 다시 쟀는데
  0.5440 → 0.5416 으로 흔들려 롤백을 냈다.
- 흔들림은 QE 가 아니라 번역에서 온다. CometKiwi 는 같은 입력 600건을 다시 채점하거나 순서를
  섞어도 차이가 0 이고 배치 크기를 바꿔도 최대 6e-6 이다. madlad 는 같은 묶음을 두 번 번역해도
  120건 중 2건이 달랐다. 번역 캐시는 20건마다만 쓰였으므로 프로세스가 죽으면 남은 번역이
  사라져 다음 실행에서 다른 문장으로 다시 만들어진다. 지금은 채점이 끝날 때마다 번역 캐시를 쓴다.

`H_set` 이 오르는데 gold 가 안 오르면 CometKiwi 를 외우는 중이다 — 거기서 멈춘다.
지금까지는 반대로 나왔다: 무참조로 고른 탐색 최적이 gold 에서도 오라클을 이겼다
(격자평균 0.7919 vs 0.7780, 네 T 전부 유의).

## 재개

`--resume` 은 같은 `--run-id` 를 이어서 돈다. 몇 시간짜리 런이라 재부팅·GPU 오류로 끊기면
처음부터 다시 도는 값이 크다.

- 이터레이션을 시작할 때마다 `state.json` 에 그때까지의 상태를 쓴다 — 완료한 이터 수, 현재
  프롬프트, 시도 이력, 체크포인트(프롬프트·출처표 포함), 시작 길이, 단위 출처표, 런 누적 지출. 임시 파일에 쓰고
  이름을 바꾸므로 쓰는 도중에 죽어도 직전 상태가 남는다.
- 재개하면 끝난 이터 다음부터 돈다. 도중에 끊긴 이터는 Critic 부터 다시 한다 — PE 가
  비결정론이라 같은 후보가 나오지 않으므로 그 이터의 채점 비용은 한 번 더 든다.
- `state.json` 이 없으면 v0 단계부터 잇는다. 이미 쓴 `prompt_v0_cand*.txt` 는 Writer 를 다시
  부르지 않고 채점한다. 분절 캐시가 프롬프트 해시로 잡혀 있어 끝난 채점은 공짜다.
- `--budget` 은 **런 전체** 상한이다. 앞선 실행 지출은 `iter_*/metrics.json` 의
  `run_total_cost`(없으면 그 실행의 `usage.cost`)와 `state.json` 중 최댓값으로 잡아 뺀다.

```bash
RUN=judge03 BUDGET=50 RESUME=1 PY=.venv-autoseg/bin/python \
  bash core/meaning_segmentator/tools/autoseg_en2x/run_judge01.sh
```

## 미해결

- **중첩 제약 하 최적을 아직 안 쟀다.** 이 값이 목표선이다. T별 최적이 서로 중첩인 문장이
  42% 뿐이라(test 100), 0.7919 는 점수 벡터 하나로 도달 불가능하다.
- **스트리밍 제약은 이 루프 밖이다.** 여기 정책은 문장 전체를 보고 순위를 매긴다. 실제
  SEG 헤드는 들은 데까지만 본다. 라벨은 그대로 쓰되 입력과 결정 규칙(전역 상위 k → 임계값)이
  달라진다. 별도 트랙.
- 집합 수준 오류(경계별로는 좋은 자리인데 조합에서 틀린 것)는 그리디 오라클에서 거의 안 나와
  다루지 않는다. 목표를 집합 탐색 최적(`--target-sets`)으로 두면 그 몫이 드러나는데, 그걸
  판단 기준 문장으로 표현할 수 있는지는 모른다. 못 하면 프롬프트가 아니라 정책 형태(집합
  인식 디코딩)로 가야 한다.
