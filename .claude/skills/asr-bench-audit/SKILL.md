# ASR 벤치 감사

수치를 믿기 전에 **측정이 모델을 재고 있는지** 확인한다. 이 프로젝트에서 결론을 뒤집은 건
지금까지 전부 모델이 아니라 측정이었다(13건, `references/traps.md`).

한 백엔드만 유독 좋거나 나쁘면 **모델 특성으로 기록하기 전에 이 감사를 먼저 돌린다.**

## 감사 순서

**0단계에서 실제로 오디오를 흘려 보고**, 그 산출물로 기계 점검(1단계)을 돌린 뒤, 거기서
못 잡는 것(2~4단계)을 사람이 확인한다. 각 단계는 **통과/실패/확인불가** 셋 중 하나로
판정하고, 실패가 하나라도 있으면 **그 수치를 보고서에 싣지 않는다.**

감사에서 나온 것을 고친 뒤에는 **0단계를 그대로 다시 돌린다.** 증상이 사라졌는지는 코드를
다시 읽어서가 아니라 전사를 다시 봐서 확인한다.

---

## 0단계 — 클립 다섯으로 e2e 스모크

**돌려보지 않으면 안 잡히는 함정이 절반이다.** 청크 경계 단어 누락, 단어 중간 공백, 전사
중복, 저레벨 빈 전사는 전부 전사를 눈으로 봐야 보인다. 1~4단계는 결과 JSON 과 코드를 읽는
사후 감사라, **결과가 없으면 감사할 대상 자체가 없다.**

### 클립은 무작위로 고르지 않는다

앞에서 N 개를 자르면 이상치가 표본에 안 들어온다(20클립 서브셋이 결론을 흔든 적이 있다).
다섯으로 줄이면 그 위험이 더 크므로 **성질로** 고른다.

```bash
python3 scripts/pick_smoke_clips.py --lang ko              # 왜 골랐는지 같이 본다
python3 scripts/pick_smoke_clips.py --lang ko --ids-only   # file_id 만
```

| 축 | 무엇을 드러내나 |
|---|---|
| 숫자 | 표기 스타일 — 아라비아로 내는 백엔드와 말로 쓰는 백엔드가 갈린다 |
| 연도 | 연도 읽기가 다른 수와 겹치는지 (2001~2009 가 21~29 와 겹친 적이 있다) |
| 단위 | `15m` 과 `15미터` 가 같은 인식으로 채점되는지 |
| 긴 것 | 꼬리 잘림, 전사 중복 |
| 저레벨 | 입력 레벨 때문에 전사가 통째로 비는 백엔드 |

`soundfile` 이 없으면 길이·레벨 축을 건너뛰고 그 사실을 stderr 에 적는다. **건너뛴 축의
함정은 이 스모크로 안 걸리므로 판정 표에 적는다.**

### 돌린다

```bash
IDS=$(python3 scripts/pick_smoke_clips.py --lang ko --ids-only)
python3 evaluation/backends/smoke_client.py --ws ws://127.0.0.1:8765 --lang ko \
  --file-ids "$IDS" --warmup --tag smoke --out smoke_ko.json
```

`--warmup` 을 빼지 말 것. 첫 요청에 모델을 로드하는 백엔드가 있어서, 그 비용이 첫 클립에
얹히면 타임아웃으로 통째로 빠진다. 50클립에서는 1/50 이라 묻히지만 **5클립에서는 20% 가
날아가고 완주 검사가 실패한다.** 실제로 Nemotron 에서 그렇게 됐다.

다섯 클립이면 1분 남짓이다. 상용 API 백엔드도 몇 센트이므로 비용은 건너뛸 이유가 못 된다.
다만 호출마다 usage 를 남기는 수단은 있어야 한다.

### 무엇을 보나 — 정답 문자열이 아니라 성질

**전사를 참조와 나란히 읽는다.** 참조가 이미 정답이므로 따로 만들 필요가 없다.

기대값을 **고정 문자열로 박지 않는다.** 백엔드마다 출력이 정당하게 다르고, 다섯 클립에서
정답과 맞아도 긴 발화의 단어 경계 버그는 그대로 남아 거짓 안심만 준다. 모델이 바뀌면
누군가 정답 파일을 고쳐 통과시키고 그때부터 검사는 의미가 없다.

실제로 이 프로젝트에서 **정답 대조로는 못 잡는 버그**가 나왔다 — 전사가 참조와 한 글자도
다르지 않은데 정규화가 점수를 0.0000 에서 0.2857 로 만든 일이다. 잡아낸 것은 불변식이었다.

그래서 보는 것은 불변식이다.

- 빈 전사 0건
- 클립당 조각 수 ≥ 2 (1.0 이면 출력 채널을 빼먹었을 가능성 — 2단계로)
- 단어 중간에 공백이 박히지 않았나 (`lag be hind`)
- 전사가 두 번 붙지 않았나 (오류율 > 1.0)
- 참조 대비 길이비 0.95~1.05
- 숫자를 아라비아로 내는가 말로 쓰는가 — **판정이 아니라 기록**이다
- 정규화가 점수를 나쁘게 만들지 않았나 (`python3 scripts/test_text_norm.py`)

앞의 다섯은 1단계 스크립트가 이미 본다. 그래서 0단계가 할 일은 새 검사를 만드는 게 아니라
**1단계가 먹을 JSON 을 싸게 만드는 것**이다. 산출물을 그대로 1단계에 넘긴다.

판정: 불변식이 하나라도 깨지면 **실패**. 고치기 전에 50클립을 돌리지 않는다.

### 작은 표본에서 흔들리는 검사는 구분한다

1단계 검사 중 **통계로 판정하는 것**(꼬리 잘림, 평균 지배, 워밍업 오염)은 다섯 클립에서
중앙값이 한두 클립에 좌우된다. 그래서 작은 표본에서는 FAIL 이 아니라 WARN 으로 나오고
표본 수를 함께 찍는다. **0단계에서 이 셋이 걸리면 본 런에서 다시 본다** — 여기서 막지 않는다.

반대로 **세면 끝나는 것**(빈 전사, 조각 수, 완주, 출력 채널, 숫자 표기)은 다섯 클립에서도
그대로 유효하다. 이쪽이 걸리면 막는다.

## 1단계 — 결과 JSON 기계 점검

```bash
python3 scripts/audit_results.py <결과JSON 또는 디렉터리> [...]
```

백엔드별 결과 JSON을 전부 넘긴다(언어별로 자동 묶는다). 확인 항목:

| 점검 | 실패 기준 | 실패가 뜻하는 것 |
|---|---|---|
| 같은 클립 | file_id 목록·총 오디오 길이 불일치 | 비교 자체가 성립하지 않는다 |
| 완주 | `n_ok < n_total`, 빈 전사 > 0 | 원인 규명 전까지 수치를 쓰면 안 된다 |
| 조건 통일 | `peak_normalize` 등 요약 필드가 백엔드마다 다름 | 조건이 다른 채로 견주고 있다 |
| 워밍업 오염 | 첫 클립 지연이 중앙값의 2배 초과 | 모델 로딩이 첫 클립에 섞였다 |
| 꼬리 잘림 | 가설/참조 길이비 중앙값이 0.95~1.05 밖 | 마지막 발화를 놓치고 있다 |
| 평균 지배 | 최악 1클립이 평균의 30% 초과 기여 | 평균 대신 중앙값도 같이 봐야 한다 |
| 숫자 표기 | 가설에 숫자가 0건인데 참조엔 있음 | ITN 차이가 오류율에 섞여 있다 |
| 조각 수 | 클립당 조각 ≈ 1.0 인데 다른 백엔드는 10+ | **출력 채널을 빼먹었을 가능성**(2단계로) |
| 재현성 | 같은 백엔드·언어 JSON 둘의 클립별 오류율 불일치 | 측정이 흔들린다 |

## 2단계 — 출력 채널 (가장 비쌌던 함정)

**이 프로젝트에서 지연을 5배로 틀리게 만든 원인이다.** 클라이언트가 `final` 만 수집했는데
한 백엔드는 미확정 가설을 `partial` 로 따로 보내고 있었다. 즉 그 백엔드만 "확정 시각"을,
나머지는 "출력 시각"을 재고 있었다.

1. 서버가 보내는 **메시지 타입을 전부 찍는다**(클라이언트 필터를 끄고 한 클립만).
2. 타입별 개수와 첫 도착 시각을 센다.
3. 백엔드마다 **화면에 뜨는 출력이 어느 타입인지** 적는다. 지연은 그 타입 기준으로 통일한다.
4. 그 출력이 **수정되는지**(revisable) 확인한다 — 수정 여부는 지연 수치가 아니라 출력 성질로
   따로 적는다. 지연 표에 축을 늘리지 말 것.

판정: 백엔드별 채널 목록이 문서에 없으면 **확인불가**로 두고 지연 비교를 보류한다.

## 3단계 — 구현 (코드 확인)

어댑터를 읽고 확인한다. 실패 시 증상은 조용하다 — 전사를 눈으로 봐야 보인다.

- [ ] **청크마다 `generate()` 를 부르지 않는가.** 매 호출이 캐시를 리셋해 청크 경계 단어가
      통째로 빠진다. 정식 스트리밍 API(제너레이터를 한 번 넘기는 방식)를 쓰는지 본다.
- [ ] **증분 출력이 단어 경계에서 끊기는가.** 델타를 마지막 공백까지만 내보내지 않으면
      소비자의 `" ".join` 에 공백이 박혀 en WER 이 두 배가 된다. **ko 로만 검증하면 못 잡는다.**
- [ ] **`finish()` 가 전사를 두 번 붙이지 않는가.** 스트리밍 누적본과 최종본을 문자열 비교로
      "조정"하면 공백 처리 차이로 매번 어긋나 전사가 반복된다(CER ≈ 1.2).
- [ ] **노브의 유효값을 확인했는가.** 무효값이 조용히 기본값으로 떨어지면 다른 이름의 같은
      결과가 저장된다. 스윕 결과 두 설정이 완전히 동일하면 이걸 의심한다.
- [ ] **모델 기본값을 config 에서 직접 확인했는가.** 문서나 기억이 아니라 `config.json` 의
      기본값 필드를 본다. "기본값 비교"가 한쪽에만 예산을 더 준 비교가 되기 쉽다.
- [ ] **전사 20개를 눈으로 읽었는가.** 위 항목 대부분은 이걸로만 잡힌다.

## 4단계 — 측정 조건과 지표

- [ ] **언어 힌트** — 지정 수단이 없는 백엔드가 하나라도 있으면 전부 주지 않는다.
- [ ] **입력 레벨** — 클립별 피크 정규화. 저레벨에서 통째로 비는 백엔드가 있다.
- [ ] **뒤 무음** — VAD 가 있는 백엔드에만. 없는 쪽엔 마지막 flush 만 늦추는 낭비다.
- [ ] **번역/후처리** — ASR 만 잴 거면 끈다. 끈 사실과 그게 유리하게 작용하는 방향을 적는다.
- [ ] **지연 지표** — 레포 표준 LAAL 을 쓴다. "오디오 끝" 기준 자체 지표는 시스템이 아니라
      **클립 길이**를 재는 값이 된다. 단위는 en 단어 / ko 글자.
- [ ] **조각 재조립** — 조각이 단어 중간에서 끊기는 백엔드는 완성된 단어에만 시각을 붙인다.
      그대로 세면 |Y_hyp| 가 부풀어 그 백엔드만 LAAL 이 왜곡된다.
- [ ] **rtf 해석** — 입력을 1배속으로 흘리면 계산 여유를 못 잰다. "따라잡았나"까지만 말한다.
- [ ] **숫자 표기** — 정규화한 값을 표에 싣는다. `scripts/itn_rescore.py` 참고.

## 보고 형식

감사 결과는 **판정 표 + 막는 항목**으로 낸다. 통과한 항목을 길게 쓰지 않는다.

```
| 단계 | 판정 | 근거 |
|---|---|---|
| 0 e2e 스모크 | 통과 | 성질로 고른 5클립, 빈 전사 0, 조각 12.9/클립, 길이비 0.99 |
| 1 기계 점검 | 통과 | 같은 50클립, 재현 일치, 빈 전사 0 |
| 2 출력 채널 | 실패 | Qwen3 만 partial 채널을 따로 보냄 — final 만 세고 있었다 |
...
막는 항목: 2단계. 지연 수치를 보고서에 싣기 전에 partial 을 포함해 재측정할 것.
고친 뒤 0단계를 다시 돌려 증상이 사라진 것을 확인할 것.
```

스모크에서 채우지 못한 축이 있으면 **그것도 적는다.** "저레벨 축 건너뜀(soundfile 없음)"
처럼 적어야, 그 함정이 안 걸렸다는 사실이 판정과 함께 남는다.

수치를 고칠 때는 **재측정이 필요한 것**(측정 자체가 틀림)과 **재채점으로 되는 것**
(전사는 있고 채점 규칙만 틀림)을 구분해 말한다. 후자에 GPU 를 쓰지 않는다.
