# asr-bench-audit — 스킬 설명서

스트리밍 ASR 백엔드의 **구현과 벤치 결과를 감사하는** Claude Code 스킬이다.
이 문서는 사람이 읽는 설명서고, 클로드가 읽는 지시문은 `SKILL.md` 다.

## 왜 만들었나

이 프로젝트에서 **결론을 뒤집은 13건이 전부 모델이 아니라 측정이었다.** 매번
"이 모델은 지연이 5배다", "이 모델은 한국어를 못 한다" 로 기록될 뻔했고, 그 중 몇은
실제로 보고서에 그렇게 적혔다가 나중에 폐기됐다.

공통점이 있었다 — **한 백엔드만 유독 좋거나 나쁘게 나왔을 때** 그걸 모델 특성으로
믿었다는 것. 이 스킬은 그 시점에 개입한다.

## 언제 쓰나

- 새 백엔드를 붙이고 첫 수치가 나왔을 때
- 벤치를 다시 돌린 뒤 **보고서에 수치를 싣기 전에**
- 한 백엔드만 결과가 튈 때 (제일 중요한 순간)
- 남이 만든 벤치 결과를 받아 검토할 때

클로드가 `SKILL.md` 의 설명을 보고 알아서 호출한다. 직접 부르려면 대화에서
"벤치 결과 감사해줘" 처럼 말하거나 스킬 이름을 대면 된다.

## 설치 위치

| 경로 | 범위 |
|---|---|
| `~/.claude/skills/asr-bench-audit/` | 이 PC 의 모든 세션 |
| 레포 `.claude/skills/asr-bench-audit/` | 이 레포에서 세션을 여는 팀원 전부 |

둘은 같은 내용이다. 고칠 때 **양쪽을 같이** 고쳐야 한다.

## 구성

```
SKILL.md                   클로드가 따르는 4단계 감사 절차
README.md                  이 문서
scripts/audit_results.py   결과 JSON 기계 점검 (표준 라이브러리만, py3.8+)
scripts/text_norm.py       표기 정규화 + 채점 (레포 evaluation/backends 와 같은 구현)
scripts/itn_rescore.py     예전 JSON 을 정규화 기준으로 환산
references/traps.md        함정 13건 + 증상→원인 색인
```

## 감사 4단계

| 단계 | 방식 | 무엇을 보나 |
|---|---|---|
| 1 | **스크립트** | 결과 JSON 의 무결성과 조건 통일 |
| 2 | 서버 찔러보기 | **출력 채널이 몇 개인가** — 가장 비쌌던 함정 |
| 3 | 코드 읽기 | 정식 스트리밍 API, 단어 경계, 중복 출력, 노브 유효값, config 기본값 |
| 4 | 체크리스트 | 언어 힌트·입력 레벨·무음·후처리·LAAL·조각 재조립·rtf 해석 |

기계로 되는 건 1단계에 몰아넣고, 나머지는 사람이 확인하도록 절차만 남겼다.
**4단계 전부 통과하기 전에는 수치를 보고서에 싣지 않는다.**

## 1단계 실행법

```bash
python3 scripts/audit_results.py <결과JSON 또는 디렉터리> [...]
```

백엔드별 결과 JSON 을 전부 넘긴다(디렉터리를 주면 하위의 `*.json` 을 모은다).
언어별로 묶어 백엔드끼리 비교한다. `{"summary": {...}, "rows": [...]}` 형식을
가정한다 — `smoke_client.py` / `smoke_voxtral.py` 의 출력이 그 형식이다.

### 출력 읽는 법

```
[ OK ] [ko] 출력 채널       qwen3_partial: 미확정 9.2 + 확정 1.2 · voxtral_sd0: 확정 31.9
[FAIL] 숫자 표기 nemotron_rc3/ko   참조 12클립에 숫자가 있는데 가설엔 0건
                                   — 재채점으로 해결(GPU 불필요)
PASS 33 · WARN 1 · FAIL 2 · SKIP 2
```

| 표시 | 뜻 | 할 일 |
|---|---|---|
| `[ OK ]` | 통과 | — |
| `[WARN]` | 자동으로 못 가른다 | 사람이 판단. 특히 "출력 채널" 경고는 2단계로 |
| `[FAIL]` | 이 수치를 그대로 쓰면 안 된다 | 아래 "고칠 때" 참고 |
| `[skip]` | 판단할 자료가 없다 | 필요하면 그 필드를 남기도록 하네스를 고친다 |

FAIL 이 하나라도 있으면 **종료 코드 1** 을 낸다. CI 에 걸어도 된다.

### 점검 항목

| 항목 | 무엇을 잡나 |
|---|---|
| 같은 클립 | 백엔드마다 다른 클립을 본 경우. 비교 자체가 성립하지 않는다 |
| 완주 | 일부 클립 실패·빈 전사. 원인 규명 전에는 수치를 쓰면 안 된다 |
| 조건 통일 | 입력 정규화·단위 같은 요약 필드가 백엔드마다 다른 경우 |
| 워밍업 오염 | 첫 클립에 모델 로딩 시간이 섞인 경우 |
| 꼬리 잘림 | 마지막 발화를 놓치거나 덧붙이는 경우 (길이비로 본다) |
| 평균 지배 | 최악 한 클립이 평균을 끄는 경우. 중앙값도 같이 보라는 신호 |
| 숫자 표기 | 한 백엔드만 숫자를 말로 써서 오류율이 부푼 경우 |
| 출력 채널 | **확정만 세고 미확정 채널을 빼먹은 경우** — 지연이 몇 배로 틀어진다 |
| 재현성 | 같은 설정 두 런의 클립별 점수가 어긋나는 경우 |

## 고칠 때 — 재측정과 재채점을 구분한다

FAIL 이 떴다고 전부 GPU 를 다시 잡을 일은 아니다.

| 종류 | 예 | 조치 |
|---|---|---|
| **측정이 틀림** | 출력 채널 누락, 조건 불일치, 지표 정의 오류 | 재측정 필요 |
| **채점 규칙만 틀림** | 숫자·단위 표기 | 전사가 JSON 에 있으니 **재채점**. GPU 불필요 |

둘을 섞어 말하면 필요 없는 런을 돌리게 된다. 실제로 그럴 뻔했다.

## 한계

- **1단계는 JSON 형식을 가정한다.** 다른 하네스의 결과에는 안 돈다.
- **2~4단계는 자동화되지 않는다.** 코드와 서버를 봐야 알 수 있는 것들이라
  스킬은 절차와 판정 기준만 준다.
- **표기 정규화는 휴리스틱이다.** 참조에 있는 수만, 문맥이 맞을 때만 되돌린다.
  못 잡는 표기가 남을 수 있고, 그 잔여는 말로 쓰는 백엔드에 **불리한** 방향이다
  (즉 순위를 뒤집는 쪽으로는 작동하지 않는다).
- **통과가 정답을 보장하지 않는다.** 이 목록은 "지금까지 실제로 걸린 것"이고,
  새 백엔드는 새 방식으로 틀릴 수 있다. 전사를 눈으로 읽는 단계를 빼지 말 것.
